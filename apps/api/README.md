# Simayi ERP API

Base backend with Bun, Elysia, PostgreSQL, Prisma, Better Auth, and Redis.

## Requirements

- Bun 1.4.2 and Node.js 24 or later.
- PostgreSQL 17 or later and Redis 7 or later.

## Local setup

From the repository root:

```bash
cp apps/api/.env.example apps/api/.env
bun install --frozen-lockfile
cd apps/api
docker compose up -d --wait
bun run db:generate
bun run db:deploy
bun run dev
```

Do not overwrite an existing `.env`. Add missing variables from `.env.example` instead.
The API listens on `http://localhost:3000`.
Open the API reference at `/openapi` and its JSON schema at `/openapi/json`.

## Configuration

Use [.env.example](.env.example) for all variable names and local defaults.
The application rejects invalid URLs, short secrets, invalid ports, and invalid origins before startup.

- Set `DATABASE_URL` and `REDIS_URL` for the target services.
- Set `BETTER_AUTH_URL` to the public API URL, not the frontend URL.
- Set `TRUSTED_ORIGINS` to comma-separated frontend origins without paths or trailing slashes.
- Set `BETTER_AUTH_SECRET` with `openssl rand -base64 48`.
- Set `MEDIA_ROOT` to an absolute, persistent directory for stored files; it defaults to `apps/api/media` and a relative or empty value is rejected at startup.

Production requires HTTPS URLs.
PostgreSQL and Redis must be available during startup.
The application never logs request bodies, cookies, or authorization headers.

## Database commands

Run these commands from `apps/api`:

| Command                                    | Use                                                          |
| ------------------------------------------ | ------------------------------------------------------------ |
| `bun run db:generate`                      | Generate the client and TypeBox models after schema changes. |
| `bun run db:migrate -- --name change_name` | Create and apply a development migration.                    |
| `bun run db:deploy`                        | Apply committed migrations in deployment.                    |

The standard `prisma.config.ts` reads only `DATABASE_URL`.
Client and TypeBox generation do not require an application secret or a running database.
`db:generate` runs both generators in `prisma/schema.prisma`: `prisma-client` writes `prisma/generated/prisma`, and the `prismabox` generator writes TypeBox schemas to `prisma/generated/typebox`.
The TypeBox generator imports `t` from `elysia` and emits `DateTime` columns as `t.String({ format: "date-time" })`, matching the JSON dates the API returns.
Both output directories are generated and gitignored. Never edit or copy them by hand, and rerun `db:generate` after a schema change.
Only the Users module consumes generated types today: its user and member DTOs use `UserPlain` and `MemberPlain` directly; the other generated models stay unreferenced.
Do not use `db:migrate` against production.

## Resource identity

Every application-owned Prisma model has two identities: an internal integer `id` (primary key, autoincrement, and the target of every integer foreign key) and a public `uuid` column (`String @unique @default(dbgenerated("gen_random_uuid()")) @db.Uuid`, database-generated random UUIDv4, not sequential UUIDv7). The UUID is the only record key the HTTP API accepts or returns; the integer `id` never appears in a DTO, response body, URL, query string, request body, error detail, or frontend state. Numeric business relation fields are renamed outward to explicit `*Uuid` fields instead of exposing the internal id, and there is no numeric-to-UUID alias, compatibility fallback, or `Number`/`parseInt` conversion of a UUID.

Public shapes: suppliers are `{ uuid, ... }`; categories `{ uuid, parentUuid, ... }`; items `{ uuid, categoryUuid, category: { uuid, name, pathstring } | null, unitUuid, unit: { uuid, name, code, active, divisible, version } | null, units, ... }`; recipes `{ uuid, scope: "company" | "local" | "customized", code: string | null, version, active, sellingPrice, priceCurrencyCode, sourceRecipeUuid, sourceVersion, sourceRecipeActive, customizationUuid, activation: { active, version } | null, ingredientCount, ... }` (branch context) with ingredients `{ kind: "item", uuid, itemUuid, item: { uuid, ... }, quantity, note } | { kind: "recipe", uuid, recipeUuid, recipe: <summary>, quantity, note }` and ingredient bodies `{ kind: "item", itemUuid, quantity, note? } | { kind: "recipe", recipeUuid, quantity, note? }`; purchase orders `{ uuid, supplierUuid, supplier: { uuid, ... } | null, responsibleUuid, ... }` with lines `{ uuid, orderUuid, itemUuid, item: { uuid, ... } | null, unitCode, currencyCode, ... }`; sales `{ uuid, recipeUuid, ... }` with ingredient snapshots `{ uuid, recipeLineUuid, itemUuid, ... }` and consumptions `{ uuid, buildComponentUuid, itemUuidRef, itemUuid, ... }`; tracking entries `{ uuid, itemUuid, userId, date, unitCode, ..., deltas }`. Native Better Auth creator/user identifiers stay opaque strings. The internal tenant id is not exported when no endpoint needs it, and the tenant is never derived from client input.

Route parameter labels are `:uuid` (`:recipeUuid` for recipes, `:deviceUuid` for the POS device segment, nested `:lineUuid` for purchase-order children); the URL shape is unchanged and only UUID values validate. Every route that shares a path segment must use the same parameter label, because Elysia's router keeps one dynamic node per segment: `/pos-devices/:deviceUuid` and `/pos-devices/:deviceUuid/z-reports/:uuid` both name the device segment `:deviceUuid`, while the nested report keeps `:uuid`. Shared DTO helpers are `resourceUuid = t.String({ format: "uuid" })` and `resourceParams = t.Object({ uuid: resourceUuid })` in `src/lib/dto.ts`. `limit`, `offset`, versions, statuses, decimals, and reference counters stay numeric; page pagination never reuses the UUID schema.

Native framework exceptions: Better Auth `user`, `session`, `account`, `verification`, `organization`, `member`, `invitation`, `team`, and `team_member` keep their framework-owned opaque string identifiers and have no `uuid` column. The canonical organization slug boundary is unchanged. `WebhookMessage` previously used a UUID `id`; its original values are preserved in `uuid` and a new integer `id` is its primary key.

The immutable sales snapshots are UUID-valued: `build.requested_recipe_uuid`, `build_component.recipe_line_uuid_ref`, `build_component.component_uuid_ref`, and `build_consumption.item_uuid_ref` stay stable after a live recipe, recipe line, or item is deleted. They carry no foreign key, so a deleted live row never nulls or rewrites historical identity. All new sales write them from the actual recipe, line, and item UUIDs inside the same transaction, and idempotent replay compares the stored `requestedRecipeUuid` and quantity before any live lookup. Existing `item_tracking.deltas` identity keys are UUID strings (`buildUuid`, `itemUuid`, `purchaseOrderUuid`, `lineUuid`).

A UUID is an identifier, not an authorization capability: every read and write still adds an explicit `organizationId` predicate, branch-owned data also carries an explicit `branchId` predicate, and the same-organization tenant boundary remains the only business access rule. A guessed or foreign-organization UUID returns the same not-found result as an unknown one and never resolves across organizations; a branch UUID from another company does not resolve either.

## Authentication contract

Better Auth owns `/auth/*`. `/me` requires a valid session cookie.
Email is not eliminated. Authentication stays on the existing Better Auth email and password flow by decision. Username sign-in without an email address is not done and waits for an architecture selection. `User.email`, `User.emailVerified`, `@@unique([email])`, session DTOs, the auth client, admin user creation, and `auth:bootstrap` stay as they are. This API does not replace Better Auth account, password, or session APIs.
Use `credentials: "include"` for browser requests.
Keep the frontend and API on the same HTTPS site, or proxy API requests through the frontend origin.
Unrelated sites require a separate cookie policy decision.

| Endpoint                                       | Request                                                              |
| ---------------------------------------------- | -------------------------------------------------------------------- |
| `POST /auth/sign-in/email`                     | `{ email, password }`                                                |
| `POST /auth/sign-out`                          | Session cookie and a trusted Origin.                                 |
| `GET /auth/get-session`                        | Session cookie.                                                      |
| `GET /auth/list-sessions`                      | Session cookie.                                                      |
| `POST /auth/revoke-session`                    | `{ token }` for the current user's session.                          |
| `POST /auth/revoke-other-sessions`             | Session cookie.                                                      |
| `GET /me`                                      | Session cookie. Safe user fields only.                               |
| `GET /auth/admin/list-users?limit=20&offset=0` | Administrator session.                                               |
| `POST /auth/admin/create-user`                 | Administrator session and `{ name, email, password, role: "user" }`. |
| `POST /auth/admin/set-user-password`           | Administrator session and `{ userId, newPassword }`.                 |
| `POST /auth/admin/revoke-user-sessions`        | Administrator session and `{ userId }`.                              |

Public registration is rejected by `disableSignUp`. Password reset and verification email are not enabled because no sender is configured. `disabledPaths` closes exactly one route, `/organization/invite-member`, so `POST /auth/organization/invite-member` returns 404 for both invitation creation/sending and resend (`resend: true` is the same endpoint). The native session, admin, and organization routes stay mounted, including `get-invitation`, `list-invitations`, `list-user-invitations`, `cancel-invitation`, `accept-invitation`, and `reject-invitation`. No invitation sender is configured, so no invitation email is delivered, and this application adds no invitation endpoint and makes no `auth.api.createInvitation` call. `/auth/organization/update-member-role` is available natively, and `PATCH /users/members/:memberId` is the application's browser path for the same native write.
The official Better Auth `admin()` plugin owns user creation, listing, password changes, and session revocation.
The frontend `/users` page calls `authClient.admin` through the official `adminClient()` plugin.
There are no custom credential CRUD endpoints and no direct Prisma credential writes. Account creation, passwords, platform roles, and session revocation stay on the Better Auth admin plugin. `PATCH /users/:id` and `PATCH /users/:id/status` are separate and are listed under Users and organizations.
`POST /users/members` and `PATCH /users/members/:memberId` accept only the native `owner`, `admin`, and `member` roles and defer to Better Auth's native authorization (`member:create`, owner-only assignment of `owner`) in the same native adapter transaction as the `auth.api.addMember` / `auth.api.updateMemberRole` write. There are no dynamic roles. Other organization member and team mutations are native Better Auth endpoints.
User creation and password changes use Better Auth's own handler; there is no custom reset hook or credential write.
Passwords require 12–128 characters. The server stores Better Auth password hashes, never plaintext.
The administrator must share initial and reset passwords through a secure channel.
This version does not force a password change after the next login.

Better Auth's native `admin` plugin grants user administration and enforces it on the server.
The migration maps existing `isSuperuser=true` users to this role.
Legacy `isStaff` and `isSuperuser` columns remain for data compatibility but no longer control access.
Inactive or banned accounts cannot use business routes: the `auth` and `tenant` macros reject them. Native `/auth/*` routes keep native behavior; Better Auth's `banned` check applies to sign-in and session creation, and this application registers no hook that rechecks existing sessions.
New records use UUID identifiers. Existing user identifiers remain unchanged.
The Better Auth `generateId` callback supplies those UUIDs. PostgreSQL `"uuid"` mode expects a database-generated id, while these Prisma models declare `String` ids without a database default; the callback fills that required native id, so no migration is needed.
Sessions expire after seven days and use HttpOnly cookies without a session-data cookie cache.
The frontend rechecks the session on navigation, window focus, and each minute in the active tab.

API errors use `{ error: { code, message, details? } }`.
Better Auth handler errors retain `{ code, message }` for compatibility with its client.
OpenAPI includes generated auth endpoints.
The `auth: true` macro verifies active identity only. `tenant: true` also requires the session's active organization and a current membership, then exposes `actor`. Business routes use `tenant: true`. `X-Organization-Id` must match that active organization when the client sends it, and the header never selects the tenant. Native `/auth/organization/*` endpoints accept their installed-plugin parameters such as `organizationId` and `organizationSlug`; this application does not pin them to the session's active organization.

### First administrator

From `apps/api`, apply the migrations and run the official Better Auth CLI:

```bash
bun run db:deploy
bun run auth:bootstrap --email admin@example.com --name Administrator
```

`auth:bootstrap` runs `auth@1.7.7 create-admin` with this application's config and the `admin` role.
The CLI prompts for a password with hidden input. There is no default account or password.
If users already exist, the CLI asks for confirmation. An existing email is rejected.
The command passes `--no-email-verified`, so it does not claim email ownership without verification.
No custom bootstrap script writes user or account records.
Do not remove the last administrator without a separate recovery procedure.
There is no public administrator recovery endpoint.

From `apps/web`, copy missing settings from `.env.example` without overwriting an existing `.env`.

## Users and organizations

`src/modules/users/` is a flat module: a single Elysia controller, static service, DTO model, and a pure output formatter.
`UsersModel.user` is the generated `UserPlain` TypeBox model itself, and the service reads the full Prisma user row: every scalar column is returned, `role`, `banned`, `banReason`, and `banExpires` keep their native nullability, and the formatter only converts `createdAt`, `updatedAt`, and `banExpires` dates to ISO strings.
The member response is the generated `MemberPlain`; the formatter only serializes its native `createdAt` date.
Request DTOs also compose the generated properties: route ids and the member body fields come from the matching generated ids and `MemberPlain`; `profileBody` picks `UserPlain` `name`/`image` and adds the HTTP bounds; `memberBody`/`memberRoleBody` refine the generated member `role`.
The status body reuses only the generated `isActive` field.
None of the generated writable input models are used.
It directly owns the account list/detail, member add, and member role update operations below.
Native authentication, platform account administration, credentials, sessions, and organization-membership persistence stay in Better Auth.
`app.ts` mounts only this controller.
Organization and team HTTP APIs are Better Auth's organization plugin under `/auth/organization/*`; dynamic access control is not enabled.
There is no shared permission package, role statement set, `AccessService`, or business permission evaluator. Business access is the same-organization tenant boundary only.

Apply `20261101150000_native_organization_tenancy` before using tenant endpoints. This document did not record that migration as applied. It creates one initial organization, copies groups to teams and `legacy_group_<id>` dynamic roles, backfills each group's `rule_set` grants onto that role once (`add` or `delete` implies `change`; `change` implies `view`; a former `admin` scope is stored only as `erp_settings`) — those are the historical names for `create`, `update`, and `read` — and backfills business `organization_id`. It does not put later writes into that organization by default.

`20261110000000_retire_custom_access` is the forward migration that retires custom access metadata. This document did not record that migration as applied. It drops only the access-only trigger and functions (`stock_item_access_before_write`, `stock_item_retain_history`, `owner_refresh_stock_access`), the `RESTRICT` foreign keys on archived `access_user_id` / `access_team_id` columns, and the access-only indexes. Every `access_*` column and row, and the `organization_role` table and rows, is retained. Check constraints are retained. It does not normalize `Member.role`; legacy custom role strings stay in place, receive no native organization privileges, and an owner or admin can reassign a native role. At that cutover Prisma marked `OrganizationRole` `@@ignore` and the retired `access*` scalars `@ignore`; the client did not expose them, and the API neither read nor wrote them. The current Prisma schema has no `OrganizationRole` model; `20261113000000_remove_legacy_schema` is the forward cleanup that drops the table, and it was applied to the local `simayi-erp`/`public` database with physical deletions; this record covers the local environment only. The earlier migration paragraphs in this document are historical cutover records, not current access instructions.

Organization lifecycle, active organization, teams, team membership, and member removal use the native organization client with `teams` enabled; `dynamicAccessControl` is not enabled. Custom dynamic roles are retired, so the native role set is `owner`, `admin`, and `member`. The `Invitation` table exists. Invitation creation, sending, and resend are closed at the HTTP boundary: `auth.ts` sets `disabledPaths: ["/organization/invite-member"]`, because Better Auth serves creation and `resend: true` on the same `POST /organization/invite-member` route, so `/auth/organization/invite-member` returns 404. The other native invitation routes (`get-invitation`, `list-invitations`, `list-user-invitations`, `cancel-invitation`, `accept-invitation`, `reject-invitation`) stay mounted, and no sender is configured, so no invitation email is delivered. Members are added explicitly through `POST /users/members` instead of an invitation. `auth.api.addMember` is server-only and pathless: the installed plugin registers no HTTP route for it, so `POST /users/members` is the application add path. `/auth/organization/update-member-role` stays mounted natively; server code also calls `auth.api.updateMemberRole` inside the business transaction, and `PATCH /users/members/:memberId` is the browser role-update path. `POST /users/members` accepts a known user id and does not search the global account directory. `GET /users` lists only members of the active organization. Platform account, password, and global user administration stay on Better Auth admin routes and require `user.role` `admin`. An organization owner does not receive those powers. Deleting the active team returns the native 403 until `set-active-team` clears it. Organization delete removes members and invitations, then the organization, in one native transaction, and does not delete teams; `Team.organization` cascades. `UserProfile` cascades with the organization. Business rows, helper rows, and owners stay `RESTRICT`; the archived stock access columns no longer block native user or team deletes.
Membership limit for `addMember` is 10000. Native organization roles do not grant platform account powers.
Deleting an organization, team, or user is a native Better Auth operation. Database foreign keys are the authority: rows with `RESTRICT` references (ERP records, owners) prevent the delete, and the driver error surfaces through the Better Auth handler. There is no occupancy preflight endpoint and no custom `409 ERP_REFERENCE` response. This application does not delete unused owners before a delete and does not clear session active-team pointers. `20261110000000_retire_custom_access` drops the retired stock-access `RESTRICT` foreign keys, so archived access metadata no longer blocks a native user or team delete.

`GET /me` returns only the account and session; there is no permission or access projection.
Lists default to 20 rows, with a maximum of 100, and accept bounded `search`.
Account creation, credentials, platform roles, and sign-in remain Better Auth admin APIs.
An organization owner cannot change platform passwords or platform roles.

### Access contract

- Business access is the same-organization tenant boundary, not an RBAC system. Every member of the active organization can read and mutate supplier, item, item-category, recipe, stock, purchase-order, sale, POS-device and finance records allowed by the company/branch scope below. The unit catalog, the currency catalog, and system preferences are global instead: authenticated accounts read them without an active organization, and only a platform administrator mutates units or preferences.
- `auth: true` verifies the active account only. `tenant: true` also requires the session's active organization and a current membership, then exposes `actor` (`TenantActor`: `userId`, `organizationId`, `branchId: number | null`, `branchUuid: string | null` in `src/lib/tenant.ts`).
- `X-Organization-Id`, when sent, must match the active organization; the header never selects the tenant.
- `X-Branch-Id` is optional and is resolved only inside that verified organization. A malformed UUID is 422 `INVALID_BRANCH_ID`; an unknown or cross-company UUID is the same 404 as an unknown branch; an inactive branch still resolves so history remains readable; absence means company context and no branch is ever chosen implicitly. Branch-only operational writes call `BranchesService.requireActor(db, actor, { active: true })` as the first statement of their transaction, which re-reads the branch under its shared lifecycle lock and rejects an inactive branch with 409 `BRANCH_INACTIVE`; a missing branch header is 400 `BRANCH_REQUIRED`. Company endpoints keep working without the branch header.
- The branch lifecycle advisory lock is two-key (`814209`, internal branch id). It must be the first advisory lock in the transaction: branch lifecycle → order `814206` → category `814202` → item `814203` → recipe `814204` → stock `814205` → finance `814207`. Branch deactivation takes the exclusive lifecycle lock and no other advisory lock.
- There is no `AccessService`, `Principal`, permission scope/action, dynamic role, record-owner visibility, or `ownership: manage` check.
- Inactive or banned accounts and removed memberships receive no business access.
- Owner and team fields are metadata only. When a record carries an owner, the service verifies that the owner exists in the same organization; it never uses the owner for authorization. Client-supplied owner UUIDs never grant access.
- Queries add an explicit `organizationId` predicate; cross-organization rows are never returned. Internal record helpers take `organizationId` immediately after `db`.
- Resource UUIDs are identifiers, not credentials or access grants. Every UUID lookup still adds `organizationId`; a foreign-organization UUID resolves to the same not-found result as an unknown one, and a numeric internal id is never accepted as a fallback.
- Only platform administrators can change platform administrator accounts.
- Assigning a native organization role follows Better Auth's rules: `member:create`/`member:update` on the caller, and only an existing owner can assign `owner`.

### Profile and ownership data integrity

The `UserProfile` and `Owner` tables stay in the database with their rows and constraints; this API no longer exposes profile or owner endpoints.
`UserProfile.active` and `type` are profile information, not sign-in flags or authorization roles.
A primary team must be one of that member's current teams in the same organization. The database invariant is `user_profile (primary_team_id, user_id)` → `team_member (teamId, userId)` with `ON DELETE SET NULL (primary_team_id)` only. Deleting that membership nulls `primary_team_id` and does not null `user_id`. Member removal deletes that user's team memberships in the same adapter transaction, so the same foreign key clears `primary_team_id`. This application adds no member-removal hook: it does not write `primaryTeamId` and does not clear `session.activeTeamId`. Session `activeTeamId` is cleared by its SetNull foreign key only when the referenced team row is deleted. Team deletion clears `primary_team_id` through that membership foreign key and through `ON DELETE SET NULL` on the team id, and clears `session.activeTeamId` through the session team foreign key. `20261101150000_native_organization_tenancy` copies `primary_group_id` only when `user_group` contained that user and group. A primary group without that membership stays empty. Session `activeTeamId` is copied only when that team membership exists. The composite foreign key `ON DELETE SET NULL (primary_team_id)` is PostgreSQL 17 SQL in that migration only. `schema.prisma` models `primaryTeam` as `primary_team_id` → `team.id` with `onDelete: SetNull` and does not emit the membership key. Regenerating a migration from the Prisma schema does not recreate it. This document did not record that migration as applied.
Profile theme and widgets remain stored. This API exposes no route that reads or edits those JSON fields. The generic `UserProfile.metadata` JSON column is removed by `20261114000000_remove_resource_metadata`.
Owner targets are a user or a team in the same organization, never both. Owner integer ids and their new public UUIDs stay stable.
Existing owner rows are not retargeted or explicitly deleted by this API.
Deleting a user or team is rejected while an owner still references them; retired stock access columns no longer block deletes. This application does not delete owner rows as part of a user, team, or organization delete.
Referenced business foreign keys use `RESTRICT`, so a deleted owner cannot become a null public owner.

The global `/users` page reads `GET /me` for the account and session and lists platform accounts through Better Auth's native admin `authClient.admin.listUsers` APIs; it does not read organization or team data. Tenant member/team management stays under `/o/$organizationSlug/settings/manage` through the native organization client, and its member add/role updates use `POST` / `PATCH` under `/users/members` with native `owner`/`admin`/`member` roles.
Server checks remain authoritative even if frontend data is stale.

## Prices and reference numbers

There is no common module, `/common` screen, exchange worker, or denomination field. Currencies are a fixed server-owned catalog, and the system currency is a global preference configured once, described below; there is still no rate table, conversion worker, or monetary aggregate.
Purchase-order and sale references use the fixed patterns `PO-{ref:04d}` and `BO-{ref:04d}` in `src/lib/reference.ts`; reference numbers never come from a stored setting row. The only stored global preference the server reads is the system currency described below.
`ModelType` remains an internal registry for notes, tags, and notifications. It has no public catalog endpoint.
`20261103000000_catalog_recipes_permissions` rewrites stored dynamic-role permission JSON keys `part_category`, `part`, and `bom` to `item_category`, `item`, and `recipe`, merging action arrays when both keys exist and preserving native and unknown keys. It drops no table. The legacy `parameter`, `parameter_template`, `part_category_parameter_template`, `part_sell_price_break`, `part_internal_price_break`, `part_test_template`, and `stock_item_test_result` tables stay in the public schema with their rows and are no longer Prisma models. Their organization foreign keys remain, so the database rejects organization deletion while historical rows exist. Do not accept a generated Prisma diff that drops them. This document did not record that migration as applied.
`20261102000000_remove_common_features` is a forward migration that drops project-code links, custom-status keys, custom units, and setting tables. This document did not record that migration as applied. Apply it in a maintenance window after a backup, with writers stopped. The script is one explicit transaction: a later failure rolls the entire scope back. Do not rewrite earlier migration files.
`20261104000000_supplier_cutover` is the forward supplier migration. It drops no table. It creates `supplier` with flat contact and primary-address fields, copies every `company` row with `is_supplier = true` using the same id, and points `purchase_order.supplier_id` and `stock_item.supplier_id` at it. A nonblank `company.contact` is preserved as the supplier contact name; contact phone and role come only from a child contact whose trimmed name matches case-insensitively, otherwise they stay empty. When `company.contact` is blank, the first child contact by id supplies name, phone, and role coherently. Customer-only and manufacturer-only companies are not copied or reclassified; they stayed in `company` as archived rows at that cutover, and the migration aborts instead of inventing a supplier when an active purchase order or supplier part points at one. `company`, `contact`, `address`, `manufacturer_part`, `supplier_part`, and `supplier_price_break` remained physically in the schema at that cutover as `@@ignore` archival models with their rows and foreign keys; no generated delegate or route read or wrote them. The current Prisma schema has none of those models; `20261113000000_remove_legacy_schema` is the forward cleanup that drops them, and it was applied to the local `simayi-erp`/`public` database with physical deletions; this record covers the local environment only. Purchase-order lines get `item_id` from the historical supplier part inside the same organization, keep the old reference as `supplier_part_id`, and snapshot `pack_quantity_native` per line. ## Currencies and system preferences

`src/modules/currencies/` serves one fixed, server-owned ISO 4217 catalog from `src/lib/currencies.ts`. There is no CRUD, rate data, auto-conversion, or multi-currency sum. The catalog is a static snapshot of the official SIX `list-one.xml` feed published 2026-09-17 (`Ccy`, `CcyNm`, `CcyMnrUnts`), so identity, display name and `fractionDigits` are deterministic and do not depend on the runtime ICU data, a database row, a dependency, or a network call. It lists active national currencies only: funds and units of account, precious metals, testing codes and the no-currency code are excluded. Codes are canonical uppercase.

Retired codes are deliberately absent: `ANG` was replaced by `XCG` on 2025-03-31 and `BGN` was replaced by `EUR` on 2026-01-01, so neither can be selected for a new default or a new line. A currency code already stored on a purchase-order line is a historical fact: it is never renamed, converted, or revalidated against the active catalog, and no line price or order total is rewritten when the catalog changes.

| Endpoint                  | Authority / purpose                                                                                                                                                                                                                                  |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /currencies`         | `auth: true`; no active organization and no tenant header. Returns `{ items: [{ code, name, fractionDigits }] }`, sorted by `code`. `fractionDigits` is the exact ISO 4217 minor-unit count (for example 0 for JPY, 3 for KWD). This is the only selectable-code list. |
| `GET /system-preferences` | `auth: true`; readable by any authenticated account so business forms work without an active organization. Returns `{ defaultCurrencyCode: string \| null }` and never creates a row. Null means not configured; no currency is ever assumed.          |
| `PATCH /system-preferences` | `auth: true` plus `UsersService.requireAdministrator(user.role)` on the verified platform account, never an organization role; a normal user receives 403 and no active organization is required. Body `{ defaultCurrencyCode: string }`, `additionalProperties: false`; it stores the currency once, the same stored code is an idempotent no-op, a different code is 409, and no request can clear or switch it. A new code must be in `GET /currencies` (422 otherwise). Returns the same shape. |

`SystemPreference` (`system_preference`) has an internal integer `id`, public `uuid`, a stable singleton `key` (unique, default `system`, database `CHECK ("key" = 'system')`), and nullable `defaultCurrencyCode`. The singleton row is created only by a PATCH, and once a code is stored the write path stays closed. The PATCH runs in one transaction under advisory lock `814208`, so concurrent initial setup stores exactly one code and takes no business lock. A missing row and a null value both mean "not configured". `default_currency_code`, `purchase_order_line_item.currency_code`, and `purchase_order_extra_line.currency_code` carry a database `CHECK` for the canonical uppercase three-letter shape only; the server catalog remains the code authority.

Purchase orders have no header currency in the model, the create/update bodies, or the response. Each item line and extra line persists `currencyCode` (`VARCHAR(3)`, nullable) as a snapshot of the fixed system currency at write time; the client never chooses it. Line creation and extra-line creation resolve the system currency inside the order transaction and return 422 when it is not configured or no longer active. A genuinely changed price writes the configured system currency, while quantity, note, discount, and echoed equal-amount edits keep the stored snapshot. Legacy lines copied from a retired order header keep that code; a line whose order had no code stays null (unknown), and no value is defaulted from the current preference. Public responses keep exact decimal strings and expose `currencyCode: string | null` on each line, where null means the historical currency is unknown.

## Media storage

All binary content lives on disk under one private root; PostgreSQL stores metadata only.
`MEDIA_ROOT` is an absolute path, defaults to `apps/api/media`, and is the only storage root: a key that is absolute, contains a parent-directory segment, or otherwise resolves outside it is rejected with 422 instead of being clamped. New uploads use a purpose directory under it; files indexed by the operational backfill keep their historical `items/images/<organization hash>/`, `supplier/images/<organization hash>/`, and `sales/batches/<organization hash>/` keys, so moving the mount only needs a copy of the whole directory.

`src/modules/media/` keeps `controller.ts`, `model.ts`, and `service.ts`. The Prisma model `MediaFile` (`media_file`) keeps one row per stored object: internal integer `id`, public `uuid`, server-generated `storageKey` (`<purpose>/<uuid>.<ext>` or a backfilled legacy key), `originalName`, the verified `contentType`, `byteSize`, `purpose` (`organization-logo`, `item-image`, `supplier-image`, `sales-batch-workbook`, `user-avatar`), `status`, nullable `organizationId`, `uploaderId`, the exact `reference`, and lifecycle fields. No row stores bytes, base64, or an absolute path, and the public projection is exactly `{ uuid, purpose, contentType, byteSize, originalName, createdAt }`. A unique `(organizationId, purpose, reference)` index enforces single binding ownership: one stored object backs at most one domain row.

An organization logo is the canonical public reference `/media/<uuid>`; that exact string is what native `Organization.logo` stores and what the native hooks accept. Legacy `data:` URIs and external `http(s)` URLs are not accepted as new values. An update that leaves `Organization.logo` unchanged keeps any historical value untouched, so an unrelated rename or slug change neither rewrites nor loses it.

An account avatar is the canonical public reference `/media/avatars/<uuid>` stored in native `User.image`. Uploads are authenticated but organization-independent: a self upload creates a temporary row owned by the uploading account, while a platform-admin target upload validates that the target account exists and creates the temporary row owned by the target so the native claim remains owner-bound. Both have no organization and expire. Attached avatars are readable by any active signed-in account (the UI renders other accounts' avatars too); unclaimed temporary avatars are readable by their uploader or by a platform administrator previewing a target upload. A native user update may set only that target account's own temporary or already attached avatar, or remove it; a changed external URL/data URI is rejected, while an unchanged historical external `User.image` remains readable and untouched until the account owner or a platform administrator replaces or removes it.

There is no public static mount, unauthenticated read, broad delete route, scheduler, token, or signed URL. Internal storage keys, integer ids, uploader ids, and lifecycle fields never appear in a response.

Lifecycle: `status` 10 is a temporary upload owned by its uploader with an `expiresAt` one day out; 20 is attached with `claimedAt`, the exact `reference`, and no expiry; 30 is deferred cleanup. `organizationId` is nullable on an attached row: deleting an organization releases every purpose it owns in the same transaction and the foreign key (`ON DELETE SET NULL`) clears the owner instead of blocking the delete. `MediaFilesService` exposes:

The disk helper writes `<key>.part` and renames it, and `remove` clears both.

The user trigger repeats the same rules authoritatively inside the native write.
- `claimImage(db, actor, purpose, reference, targetUuid)`, `releaseImage(db, organizationId, purpose, targetUuid)`, `claimWorkbook(db, actor, mediaUuid, batchUuid)`, `releaseWorkbook(db, organizationId, batchUuid)`: bindings performed inside the existing item, supplier, or batch transaction. - `discardImportedLogo(uuid)`, `discardWorkbook(actor, uuid)`, `importAttached(...)`: scoped abandonment for failed imports/creates (a private update and the server-known purpose/org/uploader, never caller input) and indexing of already stored legacy files.
- `cleanupExpired({ limit?, now? })`: reads only actionable rows (expired temporary of any purpose, or a deletion due for retry) ordered by the oldest attempt, so every pass makes progress without a cursor or resettable scan cap. Each row is owned by one conditional `UPDATE` that also excludes every committed `organization.logo` reference; only the winner unlinks, and a failed unlink keeps `deleteAttempts`/`lastDeleteError` for a later retry. Attached rows are never selected, and released rows become eligible only after the domain transaction commits.

Binding is atomic in the database, not in a hook. The migration adds the `organization_logo_media_claim_insert` (`AFTER INSERT`, so the created organization row satisfies the immediate foreign key before `media_file.organization_id` is written), `organization_logo_media_claim_update` (`BEFORE UPDATE OF logo`), and `organization_logo_media_release` (`BEFORE DELETE`) triggers on `organization`. The claim trigger runs inside the native adapter's own organization INSERT/UPDATE statement: a canonical value conditionally claims exactly one unexpired, ownerless temporary row of the logo purpose; a second concurrent request loses the row-lock race and its native write is rolled back instead of storing a logo it does not own; an already-owned row is idempotent; all other attached logos of the organization are released in the same transaction; and a missing, expired, already-bound, deleting, wrong-purpose, or newly supplied non-canonical value aborts the write. Cleanup's ownership `UPDATE` uses disjoint predicates (expired temporary or stale deleting) plus the reference exclusion, so native claim and cleanup serialize on the same row: whichever loses re-evaluates and does nothing. Rows in status 30 are never claimable, so cleanup never resurrects an active deletion.

Native hook order (Better Auth 1.7.7, verified in the installed source): permission checks run first, then `beforeCreateOrganization`/`beforeUpdateOrganization` validate the logo for an early 400 and may return normal native `data` overrides, then the adapter performs the organization write and the trigger claims/releases inside that statement. The hooks receive no database context, which is why the authoritative step is the trigger. There is no auth service, credential, session, role, or transaction replacement; a trigger rejection surfaces as a failed native write, never as a successful write with a broken logo.

Account avatars bind the same way. `20261127000000_user_avatar_media` adds the `user-avatar` purpose plus `user_avatar_media_insert` (`AFTER INSERT`), `user_avatar_media_update` (`BEFORE UPDATE OF image`), and `user_avatar_media_release` (`BEFORE DELETE`) triggers on the native `user` table. A native `authClient.updateUser({ name, image })` (and the native admin user update) runs the trigger inside its own statement: a canonical avatar claims exactly the target account's unexpired temporary avatar, releases any other attached avatar for that account first (single current avatar, serialized by the user row lock), removal releases it, an unchanged historical external value is left untouched, and any new/changed non-canonical or foreign-account reference aborts the write. A user delete releases the attached avatar before the `uploader_id` foreign key clears; unclaimed temporary avatar rows expire and the shared cleanup removes their bytes and staging files. The native `databaseHooks.user.update.before` adapter only rejects early with a 400; it does not reimplement users, passwords, sessions, or admin authority.

Image validation is centralized in `src/lib/images.ts` (`imageMaxBytes`, `verifyImageBytes`, `readImageUpload`) and reused by item images, supplier images, organization logos, account avatars, and the historical import: PNG, JPEG, or WebP up to 1 MB, kind taken from the magic signature. Workbook uploads keep their own 10 MB limit and parsing in `src/modules/sales/batches/`.

### Media operator commands

Run these from `apps/api`. None is an HTTP route, and none is a scheduler.

```bash
bun run media:migrate-logos --dry-run          # decode/verify historical logos, no writes
bun run media:migrate-logos --batch 200        # import every historical data: logo
bun run media:backfill-consumers --dry-run     # verify/index legacy images and workbooks, no writes
bun run media:backfill-consumers --batch 200   # index every existing item/supplier image and workbook
bun run media:cleanup --limit 500              # remove due deferred files and abandoned uploads
```

`media:migrate-logos` pages through **every** organization by id until the set is exhausted (`--batch` bounds the page, not the total scan), so a rerun never stalls on the first page; an interrupted run is restarted and already-canonical rows are skipped. For a `data:` URI it decodes the payload, verifies it with the shared image contract, writes one unclaimed `media_file` row and its bytes, and replaces `organization.logo` only with `WHERE id = ... AND logo = <original value>`; the trigger claims the temporary file in that same update. A conditional miss or update failure marks the new file for cleanup instead of overwriting. A malformed or oversized `data:` value, an unknown scheme, or a canonical reference with no media row is reported per organization and fails the run (exit 1) without changing that logo. Historical `http(s)` logos are counted and preserved unchanged by policy: they are not fetched server-side and no base64 fallback exists. A native update that omits `logo` leaves such a value untouched (the web form omits an unchanged logo), while any attempt to send `data:` again is rejected. Run this import to completion before starting the new API, following the deployment order below.

`media:backfill-consumers` is the explicit, idempotent, non-destructive import for the existing consumer files. It pages every item, supplier, and sales batch by id to exhaustion (`--batch` bounds the page, not the total scan; an interrupted run is restarted and already indexed rows are skipped). Existing `Item.image`, `Supplier.image`, and `SalesBatch.sourceFile` references are preserved: the script only verifies the already stored bytes (signature/kind or xlsx/size), then creates an attached `media_file` row whose storage key is the historical private path and whose single-target binding is `item:<uuid>`, `supplier:<uuid>`, or `sales-batch:<batchUuid>`. A stored file that is shared by more than one record fails explicitly instead of being counted as already indexed; a matching row must agree on organization, purpose, target binding, identity, and attached status. Missing, malformed, oversized, mismatched, or unsupported files are reported per record with a fixed path-free reason and fail the run without changing or dropping anything. Historical external `http(s)`/`data:` image values are counted and preserved unchanged; nothing is fetched remotely. `--dry-run` performs the full scan and verification without writing. **The API must not be writing during the import**: the script cannot atomically prove a reference did not change under live writers, so stop the API before running it. There is no dual-read legacy fallback: after the backfill, the new API reads only `media_file`.

`20261125000000_media_files` is the additive migration that creates `media_file` with its indexes (including the unique single-binding index), foreign keys, check constraints, and the organization logo claim/release and all-purpose delete triggers; it changes no existing table or row. It was applied to the local database via `bun run db:deploy` (reported by the supervisor). `20261126000000_fix_media_logo_trigger_reference` is a forward-only replacement of just that trigger function: the PL/pgSQL variable named `reference` was renamed `logo_reference`, which resolves the PostgreSQL 42702 ambiguous-column error in `SET "reference" = reference` that any logo-bearing native organization update hit. Trigger timings, binding, release, and safe-deletion behavior are unchanged; no table, row, column, index, constraint, or applied migration file is modified. `20261127000000_user_avatar_media` is the next forward-only migration: it adds the `user-avatar` purpose to the purpose check and the native user avatar claim/release/delete triggers. All three media migrations have now been applied to the local development database via `bun run db:deploy` (reported by the supervisor); this document does not claim they are applied to any other database. The existing migration files remain untouched.

### Media deployment order and backup

Only metadata is in PostgreSQL; the bytes are in `MEDIA_ROOT`. Back up and restore both together (a filesystem snapshot plus a database dump, or a quiesced copy), otherwise the database references files that do not exist. `MEDIA_ROOT` must be a persistent mount before the new code runs.

With the API stopped (no live writers), a verified backup of the database and `MEDIA_ROOT`, and the media mount in place:

1. Apply the media migrations with `bun run db:deploy` (`20261125000000_media_files`, the forward `20261126000000_fix_media_logo_trigger_reference` function replacement, and `20261127000000_user_avatar_media`; fresh databases receive them in order). The local development database already has all three applied; any other environment must still run this step.
2. Run `bun run media:migrate-logos --dry-run`, review `external`/`failures`, then run it to completion.
3. Run `bun run media:backfill-consumers --dry-run`, review `external`/`failures`, then run it to completion.
4. Start the new API. Existing item/supplier images, source workbooks, and logos are served from the indexed rows; there is no legacy path reader.
5. Schedule `bun run media:cleanup --limit 500` (hourly is sufficient) in the deployment job set. It is bounded, removes expired unclaimed uploads of every purpose, released images/workbooks, retry `.part` artifacts, and retries failed deletions without deleting attached or referenced files.
6. An organization delete releases all of its attached media in the same transaction; the foreign key is `ON DELETE SET NULL`, so media never blocks the delete and deferred cleanup collects the files.

Residual `failures` from either import are loud and leave the affected record untouched; resolve the underlying file and rerun the idempotent command.

## Branches

`src/modules/branches/` keeps `controller.ts`, `service.ts`, `model.ts`, and a pure `formatter.ts`. A branch belongs to exactly one company (native organization) and is never deleted: deactivation keeps stock, sales, receipts and POS history attributable.

| --- | --- |
| `GET /branches/?limit=&offset=&search=&active=` | Company-scoped paged list `{ items, total, limit, offset }`; each item `{ uuid, name, description, active, version, createdAt, updatedAt }`. `active` is optional. |

## Items

`src/modules/items/` keeps `controller.ts`, `service.ts`, `model.ts`, and a pure `formatter.ts`. An item is an ordinary physical material. The Prisma model keeps the physical `Part`/`part` names and, outward, exposes exactly `uuid`, `organizationId`, `name` (at most 100 characters, nonblank), `description` (at most 250, default empty), `categoryUuid`, a nullable global-catalog `unitId` relation reported as `unitUuid` plus `unit: { uuid, name, code, active, divisible, version } | null`, the computed `units` display string (the assigned unit code, `""` while unresolved), `image` (at most 100, nullable), `ipn` (at most 100, nullable), `defaultExpiry` (nonnegative integer, default 0), `active` (default true), `creationDate` (day `YYYY-MM-DD`), `creationUserId`, and `version` (default 0); the internal integer `id`, `categoryId`, and `unitId` are not public. It has no persisted free-text unit column: `units` is derived from the relation. It has no template, variant, revision, lock, trackable/testable/purchaseable/salable, virtual, consumable, assembly/component, BOM validation, barcode, metadata, keyword, link, owner, base/maximum stock, multiple, lot, batch, serial, expiry, or supplier field; name and IPN are not unique. Stock and minimum stock are not item columns: each branch/item balance lives in one `BranchStock` row (`stock` `Decimal(20,5)`, `minimumStock` `Decimal(19,6)`, own `version`), and a missing row reads an exact zero without creating it. The item response returns those retained fields plus `category: { uuid, name, pathstring }` and the unit projection above; branch balances are exact decimal strings in HTTP, never JavaScript numbers.

`BranchStock` is the single aggregate balance per branch and item. There is no per-lot stock record, and the model has no lot status, serial, batch, expiry, or location; aggregate before/after are the only balance transitions new writes record, while copied historical tracking deltas and the original consumption transitions stay recorded exactly as they were. Every balance write goes through `ItemStockService` in `src/modules/items/stock/`: `lock(db)` takes the existing stock advisory lock `814205`, `quantity(value, allowZero)` parses an exact decimal string at scale 5 with 15 integer digits, `change(db, actor, itemId, operation, quantity, options)` updates the selected branch's balance for an existing same-organization item and increments the branch-stock `version` once while recording one branch-tagged tracking row in the same transaction, and `record(...)` writes the ledger row for a balance write inside the same lock. Manual add, remove, and count, sale consumption, and purchase receipt all use this one ledger; item create/update no longer writes stock. A legacy item with no assigned unit is rejected with 422 for every balance write, including purchase receipt and stock adjustment, until a unit is assigned; no movement is ever recorded with an unknown unit code. A zero count keeps the item alive; nothing deletes an item or a balance row when stock reaches zero. Tracking types keep their older meanings: `1` legacy create baseline (copied history only; new item creation writes no balance), `5` edit (legacy only), `10` count, `11` add, `12` remove (sales use it with sale context), `70` purchase receipt, and `90` migration baseline. New rows always store the real aggregate before and after amounts; historical lot events may leave them null instead of inventing a value, so before/after keep their real storage meaning.

Item create, update, and delete take the catalog lock `814203`; they no longer change a balance, so the stock lock is not part of a catalog write. Branch balance writes take `814205`. Purchase receipt (`POST /order/purchase-orders/:uuid/receive`) takes one non-empty array of selected lines, with no upper array cap; each entry may name a destination `branchUuid` inside the same company (defaulting to the order's origin branch, explicit for a company-origin order), and the receipt writes only that branch's balance through `ItemStockService.change` with tracking type `70` inside the existing order transaction. It keeps the order/outstanding/price checks, records the immutable `PurchaseReceipt` event, and returns `{ orderVersion, receipts }`.

`GET /items/?limit=&offset=&search=&categoryUuid=&subcategories=&active=` lists same-organization items ordered by name then id. `search` is a bounded case-insensitive match on name, description, and IPN; `categoryUuid` filters one category and `subcategories=true` includes its descendants; `active` is optional. Those are the only filters; the removed variant, revision, template, and purchaseable filters do not exist as aliases. `GET /items/:uuid` returns one item. Both reads are scoped to the active organization and return catalog fields only; balances and minimums come from the branch stock endpoints below.

`POST /items/` and `PATCH /items/:uuid` use an explicit writable allowlist with `additionalProperties: false`: `name`, `description`, `categoryUuid`, `unitUuid`, `image`, `ipn`, `defaultExpiry`, and `active`. Stock and minimum stock are not accepted here and are written only through the branch stock endpoints. `name` and `unitUuid` are required on create; `PATCH` accepts an optional `unitUuid` but never `null`, and a legacy `units` free-text field is rejected by validation instead of being written. `organizationId`, `creationDate`, `creationUserId`, `unit` and `version` are set by the server. The response keeps the computed `units` display string (the assigned unit code, or `""` while unresolved) and adds `unitUuid` plus `unit: { uuid, name, code, active, divisible, version } | null`; `units` is derived from the relation and is not a second writable source. A new item must reference an active global-catalog unit. On update, an inactive already-assigned unit may stay, but a newly selected unit must be active; changing an already-assigned unit is rejected with 409 while the item has nonzero stock, any recipe/order/sale link, or meaningful tracking history, while an unresolved legacy item may still be explicitly assigned even with legacy balances. Those invariants are checked under the catalog lock; branch balance writes take the stock lock separately. Item create/update never writes a balance, and a branch balance row is created only by a branch stock write. `PATCH` requires a `version` property in the body; omitting it fails request-schema validation (422). A present `version` must equal the stored version, a stale number returns 409, and one successful update increments `version` once, even when several catalog fields change together. Every route uses the `tenant: true` actor and scopes reads and writes by `organizationId`; there is no permission scope, dynamic role, or record-owner check.

Branch stock routes live under `/stock/`; the branch header is optional for listing and required for writes. Without `X-Branch-Id`, `GET /stock/` lists paginated item × same-company-branch positions, including inactive branches for history, with bounded `limit`/`offset` and optional `search`, `categoryUuid`, `subcategories`, `active` (item) and `low`; each row adds `branch: { uuid, name, active }` equal to `branchUuid`, and `total` is the exact position count, so one item can appear once per branch. With `X-Branch-Id` the same enriched list is restricted to that branch. `GET /stock/:uuid` returns one item's balance in the required branch as `{ itemUuid, branchUuid, ...catalog fields, stock, minimumStock, version, belowMinimum }` where `version` is the branch balance version; `PATCH /stock/:uuid` changes only the minimum with `{ version, minimumStock }`; `POST /stock/:uuid/add`, `/remove` and `/count` accept `{ quantity, version, notes? }`. A missing row reads zero stock and zero minimum and is never created by a read. `quantity` is an exact decimal string; add and remove require a positive amount, count accepts zero or more, and a result below zero or above the decimal bound is rejected before any write. `version` must equal the stored balance version and a stale number returns 409; one successful adjustment increments it once while writing one branch-tagged tracking row. `GET /items/:uuid/tracking/` with bounded `limit` and `offset` lists the same-organization tracking rows, filtered to the resolved branch when a branch header is present; each entry is `{ uuid, itemUuid, branchUuid, trackingType, date, notes, userId, deltas, quantityBefore, quantityAfter, unitCode }` where before/after are decimal strings or null and `unitCode` is the exact unit code captured when that movement was written (`null` for legacy rows whose historical unit is unknown). `deltas` keeps its business context and carries UUID identity strings for `buildUuid`, `itemUuid`, `purchaseOrderUuid`, and `lineUuid`. The organization and branch always come from the verified actor; no organization or branch parameter selects scope. There are no stock-item create, update, or delete routes and no `/stock-items` or `/items/:uuid/stock-history` aliases.

`src/modules/items/images/` keeps the item image submodule as a thin adapter over `MediaFilesService`. `POST /items/images/` accepts `multipart/form-data` with one `image` file field and returns `201` `{ image }` with the unchanged public reference `/items/images/<uuid>.<png|jpg|webp>`, which fits the 100-character `Item.image` bound and stays directly renderable. Only PNG, JPEG, and WebP up to 1 MB are accepted by the shared validator, the kind comes from the magic signature, and the bytes are stored under `MEDIA_ROOT/<purpose>/<uuid>.<ext>` with metadata (purpose, organization, uploader, verified type, size, expiry). The upload is temporary. `POST /items/` and `PATCH /items/:uuid` validate the reference and bind it with a conditional claim inside the existing serializable catalog transaction: the file must be this organization's, this uploader's, the item-image purpose, and unexpired; an already attached identical binding is idempotent. An unchanged historical external image value is preserved without rewriting, while a changed non-media value is rejected. Replacing, clearing, or deleting an item releases only that binding in the same transaction; the bytes are removed later by deferred cleanup. `GET /items/images/:fileName` keeps `tenant: true`, resolves the uploader's unexpired temporary file for a failed save preview, serves attached files to every same-organization member with the stored content type plus `Cache-Control: private, no-store` and `X-Content-Type-Options: nosniff`, and answers 404 for a cross-organization, wrong-purpose, expired, or deleting file. There is no public static mount, unscoped file read, delete endpoint, image processing, or signed URL.

Applying `20261111000000_simplify_items` is a precondition for this shape. This document does not record that migration as applied.

## Units

`src/modules/units/` keeps `controller.ts`, `service.ts`, and `model.ts`. A unit is one global catalog row (`unit`) shared by every organization: internal integer `id`, public `uuid`, `name` (at most 100 characters, nonblank), `code` (at most 20 characters, nonblank, globally unique), `active` (default true), `divisible` (default true) and `version` (default 0). There is no `organizationId` on the row and no tenant relation; `part.unit_id` is a nullable single-column foreign key to `unit.id`. `divisible` is descriptive metadata: it records whether the measurement splits into fractions (for example kg) or only whole pieces (for example adet), and no quantity, stock, recipe, order, sale, rounding or conversion rule reads it.

| Endpoint                                    | Authority / purpose                                                                                                                                                                                                                                                                                                     |
| ------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /units/?limit=&offset=&search=&active=` | `auth: true`; no active organization or tenant header. Lists the global catalog ordered by name then id. `search` matches name and code case-insensitively; `active` is optional. Response `{ items, total, limit, offset }`, each item `{ uuid, name, code, active, divisible, version }`.                                      |
| `GET /units/:uuid`                          | `auth: true`; one global unit.                                                                                                                                                                                                                                                                                         |
| `POST /units/`                              | `auth: true` plus `UsersService.requireAdministrator(user.role)` on the verified platform account; body `{ name, code, active?, divisible? }`, `additionalProperties: false`; returns `201` with the unit; omitting `divisible` stores `true`. | `PATCH /units/:uuid`                        | Platform administrator only. Body `{ version, name?, code?, active?, divisible? }`. The stored `version` must match or the request returns 409. Reads never mount the tenant macro, so catalog pickers work for a normal member with no active organization. Writes use the verified platform role only (`UsersService.requireAdministrator`, checked against the signed-in account's `user.role`), never an organization role. A normal authenticated user receives 403 and cannot mutate the catalog.

Usage checks span every organization: the service counts `part` rows by `unitId` with no organization predicate before a code change or a delete. Writes run through the catalog transaction (serializable, advisory lock `814203`), the same lock item creation and unit assignment use, so a delete or code change cannot interleave with an item selecting that unit. Deactivating a unit is allowed and never rewrites an existing item assignment or a historical snapshot; an inactive unit stays readable and valid for items that already use it, but it cannot be newly assigned, and item creation requires an active unit. Reassigning an item's unit is refused (409) once the item has a nonzero balance, a recipe/order/sale reference, or meaningful tracking history; a legacy item with no unit may be assigned one explicitly (that assignment labels the item's existing aggregate balance with the chosen unit and performs no conversion; existing snapshot columns are never rewritten). There is no package/multiple conversion and no implicit conversion between units.

Applying `20261119000000_units` is a precondition for this shape. This document does not record that migration as applied. That migration maps each DISTINCT nonblank `part.units` label in one organization to exactly one unit whose `name` and `code` are that unchanged label, sets `part.unit_id` by that exact label match, leaves null/blank labels unresolved, adds nullable `item_tracking.unit_code` and `purchase_order_line_item.unit_code` without backfilling them, and only then drops `part.units`. It does not interpret aliases, convert quantities, or infer a past unit from today's item.

Applying `20261121000000_system_units_currency` globalizes that catalog. It is one explicit `BEGIN`/`COMMIT` block with `ACCESS EXCLUSIVE` locks on `unit`, `part`, `item_tracking`, `purchase_order`, `purchase_order_line_item`, and `organization_preference`, so it runs in a maintenance window with API writers stopped. Rows that share a `code` across organizations are merged only when every definition is exactly equivalent (identical `name` and identical `active`); the survivor is the lowest `id`, so its `uuid` and `version` stay stable. Every `part.unit_id` that referenced a retired duplicate is rewritten to the survivor (the item's unit code, name and active flag are identical, so only the internal key changes), each retired duplicate uuid is reported with `RAISE WARNING` before it is deleted (capture the migration output as the record), `organization_id` is dropped, and `code` becomes globally unique. Any code whose definitions differ in `name` or `active` aborts the whole transaction with the offending codes and counts instead of guessing. No item balance, purchase-order reference/price/total/currency, tracking row, or sales snapshot is rewritten, and the `unit_code` snapshot columns are untouched.

Applying `20261203000000_unit_divisibility` adds `unit.divisible BOOLEAN NOT NULL DEFAULT TRUE` and is a precondition for this shape. This document does not record that migration as applied. It runs after `20261202000000_company_branches`, gives every existing unit `true` (preserving the previous decimal-capable behavior), and defaults a new row to `true` when the caller omits the flag. Nothing is inferred from a unit's name or code, no row is removed, and the flag is not read by any stock, recipe, order, sale, rounding or conversion path.

## Recipes

`src/modules/recipes/` keeps `controller.ts`, `service.ts`, `model.ts`, and a pure `formatter.ts`. A recipe is an independent record, not an item view. The `Recipe` model (`recipe`) has an internal auto-increment integer `id` (not public), a public `uuid`, `organizationId`, a nullable `branchId`, a nullable `sourceRecipeId`, a nullable `sourceVersion`, `name` (at most 100 characters, nonblank), a nullable `code` (at most 100 characters, the trimmed exact external product code: leading zeros are significant, comparison is case-sensitive, and duplicates are allowed as metadata), `description` (at most 250, default empty), `active` (default true), `sellable` (default false), a nullable `sellingPrice` (`DECIMAL(19,6)`, nonnegative), its `priceCurrencyCode` snapshot, `version` (default 0), and `createdAt`/`updatedAt` timestamps. Three scopes share one table and are enforced by `recipe_branch_source_scope_check` plus `recipe_scope_guard`: `branchId` null with no source is a company template; a non-null `branchId` with no source is a branch-local recipe; a non-null `branchId` with `sourceRecipeId` and `sourceVersion` is a branch's full customization of one company template. Branch scope and source pin are immutable after insert; a reset deletes the customized row explicitly. `code` behaves like the other content fields: a company edit reaches uncustomized branches, a full customization copies the company code and may pin its own value, and a reset restores the company code. It is never derived from a name, an item IPN, or a legacy product mapping, and no uniqueness constraint exists. A missing price means the recipe is unpriced, which is distinct from a zero price; existing recipes stay unpriced and are never backfilled. Setting a price captures the fixed system currency and a price in any other currency is impossible because the currency is never client-supplied. Re-sending the stored amount is a no-op that keeps the recorded price currency snapshot, so a name or ingredient edit never relabels a legacy price; only a genuinely changed amount captures the fixed system currency. A sale still requires the recorded organization money currency to match, so a legacy finance snapshot in another currency fails clearly instead of mixing amounts. Clearing the price sends an explicit `null` and only affects future sales; recorded sale snapshots never change. `sellable` is an independent flag, not a second activation: `active` plus the branch activation decide whether a definition is available in a branch, while `sellable` only allows a direct sale of it, so a nested ingredient recipe never has to be sellable or priced. A sellable recipe must persist both a selling price and its currency snapshot (zero is a valid price); the merged persisted state is validated before every create, update and customize, so marking an unpriced recipe sellable or clearing the price of an already sellable one returns 422 `RECIPE_PRICE_REQUIRED` before any write. A create that omits `sellable` stores `false`, a patch that omits it keeps the current value, an explicit `false` never clears an existing price or currency, a full customization copies the company value and may pin its own, and a reset returns to the company value. The database enforces the same implication with `recipe_sellable_price_check` in the `20261205000000_recipe_sellability` migration, which also backfills `sellable = true` for definitions that already carry both a price and its currency. The `RecipeLine` model (`recipe_line`) has an internal auto-increment integer `id` (not public), a public `uuid`, `organizationId`, `recipeId`, a nullable `itemId`, a nullable `childRecipeId`, `quantity` `Decimal(15,5)` greater than zero, and `note` (at most 500, default empty), with `UNIQUE(recipe_id, item_id)` and `UNIQUE(recipe_id, child_recipe_id)`. Exactly one of `item_id` and `child_recipe_id` is set: a database check rejects neither or both, so one line is either an item ingredient or a reference to another recipe. Lines are returned ordered by id. An item ingredient must be an existing, active item in the same organization with a resolved unit; the `units` shown in responses is that unit's code, and a unit-less legacy item is rejected instead of being assigned a guessed unit. A recipe reference must be an existing, active recipe resolvable in the same context and is never merged into the parent: it stays one line whose quantity means "units of the child recipe per one unit of this recipe". Company context only references company templates, so a shared recipe can never depend on a branch-local definition. Branch context stores the canonical identity (company template or that branch's local recipe), so the child is resolved through the branch's own customization when one exists; another branch's definitions, a customization row's UUID, and a company template that is not activated in the branch are rejected. Both same-organization compound foreign keys are `RESTRICT`, so deleting an item or a referenced child recipe never deletes a recipe line. A recipe graph may nest to any depth, may reuse the same child recipe on several lines or paths, and may not contain a cycle, directly or indirectly; a repeat of the same item or the same child recipe inside one parent is rejected instead of being merged. There is no assembly or component distinction, no inherited/template chain, no checksum or validation step, no optional/consumable/setup/attrition/rounding semantics, no substitutes, and no separate nested line endpoints: children are edited as ordinary lines of their own recipe.

An absent `BranchRecipe` assignment means `branchActivation = true` at version 0 in every existing and future branch; an explicit `active: false` remains an opt-out. Reads create no assignment rows. Effective availability is `companyActive && branchActivation` for shared definitions and the row's own `active` for local recipes, so a globally disabled company template blocks every branch while its historical sale snapshots stay unchanged; a company edit never overwrites a customized branch, and branch content/name/price stays isolated. Effective `sellable` is content of the definition that would be sold, so it is independent of both gates and a branch customization pins its own value.

A recipe cannot contain the same item twice or the same child recipe twice; a duplicate reference in one body is rejected with a clear error instead of being merged or dropped, and differently-cased spellings of one UUID resolve to the same identity. A child reference must be active in the context and must not be the edited recipe itself. The effective graph is walked under the recipe lock before the write, so a direct or indirect cycle is rejected with 422 even when two opposing edits race: both mutations serialize on advisory lock 814204. A branch write only checks its own branch; a company edit also resolves the effective graph of every branch that owns a customization, because a shared edge can close a cycle through a branch's customized child. Reset re-checks the resulting effective graph, and activation refuses to expose an already cyclic graph. Errors use the standard `{ error: { code, message, details? } }` envelope. Recipe mutations take the branch lifecycle lock first when a branch is required, then the catalog and recipe locks (814203, 814204), and never touch stock. The global lock order is branch lifecycle (814209, branchId), order 814206, category 814202, catalog 814203, recipes 814204, stock 814205, finance 814207. Item create/update/delete take catalog then stock; recipe operations take the branch guard, catalog, then recipe; sales and batch processing take the branch guard, catalog, recipe, stock, then finance. No path acquires the branch lifecycle lock after another advisory lock. The recipe lock uses `814204` through `$executeRaw`, because `pg_advisory_xact_lock` returns `void`, which the Prisma PostgreSQL adapter cannot deserialize as a `$queryRaw` column.

Applying `20261109000000_restaurant_recipes` is a precondition for these routes, and `20261201000000_recipe_nested_ingredients` is required before any recipe line can reference another recipe; branch scoping additionally requires `20261202000000_company_branches`, which adds the branch/source columns, the `branch_recipe` activation table and the scope/source guards. The local `simayi-erp` / `public` deployment, including both latest migrations, is recorded in `../../docs/company-branch-cutover.md`; deployment state in other environments must be verified separately. Every recipe route uses the `tenant: true` actor and scopes reads and writes by `organizationId`; `X-Branch-Id` optionally narrows the request to one same-company branch and is validated by the branch guard. There is no permission scope, dynamic role, or record-owner check.

## Purchase orders

`src/modules/order/purchase-orders/` keeps `controller.ts`, `service.ts`, `model.ts`, and `formatter.ts`, with the `lines`, `extra-lines`, and `receive` submodules nested under it. `GET /order/purchase-orders/?limit=&offset=&search=&supplierUuid=&status=&open=&branchUuid=` lists same-organization orders; company context sees every origin, while a branch context or explicit `branchUuid` filter narrows the list to that order origin. `POST /order/purchase-orders/` creates the root with an optional `branchUuid` origin (`null` is company-origin, an omitted field follows the caller's selected branch, and an explicit `null` always creates a company-origin order), `GET /order/purchase-orders/:uuid` returns one order, and `PATCH /order/purchase-orders/:uuid` updates it with the stored `version` in the body. Status actions are `POST /order/purchase-orders/:uuid/place`, `/hold`, `/cancel`, and `/complete`; each takes `{ version }` (complete also accepts `acceptIncomplete`) and a stale version returns 409. Order, line, and extra-line responses are keyed by `uuid`; the supplier and responsible references are `supplierUuid` and `responsibleUuid` with nested `supplier`/`responsible` projections keyed by `uuid`, and receive bodies are `{ version, requestKey, items: [{ lineUuid, branchUuid?, quantity, notes? }] }`.

Order headers carry no `currencyCode`, and the create/update bodies accept none. Each line response exposes its own `currencyCode: string | null`; creation writes the fixed system currency snapshot inside the order transaction (422 when it is not configured or retired), a genuinely changed price rewrites that snapshot, and an echoed equal amount keeps it. Line creation snapshots the item's current unit code as `unitCode` and requires the item to have a resolved unit; updating an unchanged legacy line does not require one, while changing its item snapshots the new item's unit. Line responses expose `unitCode: string | null` where null means the historical unit is unknown. Extra lines carry their own `currencyCode` snapshot and have no unit semantics. Line writes hold the order lock and then the stock lock (`814206` then `814205`), so they serialize with item unit reassignment.

Creating an order also creates its single finance purchase movement (`money_movement` kind `60`, `status` 10) in the same transaction, so the reservation always exists from creation. It is keyed to the order through `purchase_order_id` (one row per order), uses the fixed organization finance currency (the first purchase write creates the `organization_finance` row; a missing system currency is 422 and a stored legacy code that differs is 409), holds `0` with `pricing_incomplete` while the order has no priced line, and otherwise holds the known priced subtotal, item and extra lines at `quantity × price × (1 − discount/100)`, stored as the negative outflow it anticipates. Only amounts recorded in the finance currency are summed: a line with no price, no currency, or another currency is counted in `pricing_issue_count` and flagged instead of being treated as a zero cost or added across currencies. Every item-line and extra-line add, edit or delete, and every header edit, refreshes that row in the same transaction after the order and stock locks.

There is no `DELETE /order/purchase-orders/:uuid`, no root destroy service method, and no root `purchaseOrder.delete` path: a purchase order cannot be deleted. `POST /order/purchase-orders/:uuid/cancel` is a status transition only. It moves a pending (`10`), placed (`20`), or on-hold (`25`) order to cancelled (`40`) with the usual version claim, and keeps the order, its lines, extras, receipts, and already received stock history unchanged. The same transaction releases the finance reservation (`status` 30), so a cancelled order leaves both the hold and the cash balance and never debits cash. Completed (`30`) and cancelled (`40`) orders reject place, hold, cancel, and complete.

`POST /order/purchase-orders/:uuid/complete` is the only transition that turns a reservation into cash and settles the supplier payable. Inside the same serializable transaction it first requires a same-organization supplier, at least one item or extra line, a price on every item and extra line (a zero price is valid, a missing price is 422), and priced lines that all record one currency equal to the organization finance currency (a priced line without a currency or mixed line currencies is 422; a stored finance code that differs from the fixed system currency is 409), then it recomputes the exact final total from that one currency, claims the version, sets status `30`, and finalizes the order's single finance purchase movement: its `status` moves from `10` (on hold) to `20` (posted) and its negative amount becomes the exact total, so the cash balance drops exactly once. The retained purchase debit (kind `20`) is settled by one equal auto-posted payment credit (kind `30`) in the same transaction: the debit keeps only its `purchase_order_id`, and the credit carries both that order link and the unique `money_movement_id` of the purchase movement, so a newly completed purchase leaves no unpaid amount and the generic reversal finds the credit through that link. A zero total posts no supplier row because no debt exists. Unique `(organization_id, purchase_order_id)` indexes keep both postings exactly once, and already completed or cancelled orders cannot re-enter. Draft, place, hold and receive write no payable and no cash movement and keep the reservation; cancel releases it without any cash debit. Previously completed orders are never backfilled. The finance advisory lock `814207` is taken after the order lock `814206`, and no catalog, recipe, stock or order lock is acquired afterwards.

`GET /order/purchase-orders/:uuid/receipts/?limit=&offset=&lineUuid=&branchUuid=` lists the immutable delivery events (optional line/destination filters) as `{ items, total, limit, offset }`, and `POST /order/purchase-orders/:uuid/receipts/:receiptUuid/reverse` writes one compensating event with `{ version, notes?, requestKey? }` and returns `{ orderVersion, receipt }`. A receipt row exposes `{ uuid, orderUuid, lineUuid, branchUuid, branch: { uuid, name, active }, itemUuid, quantity, stockQuantity, unitCode, packQuantityNative, purchasePrice, discount, currencyCode, notes, userId, occurredAt, legacyBaseline, reversalOfUuid, reversalUuid }`. Receipts are immutable evidence per order line and destination branch: each event snapshots quantity, stock quantity, pack, unit, purchase price/discount and currency, plus actor/time/notes and a request key; the parent order keeps the current net received quantity and version. A correction never deletes or edits the original, reverses each event once (`reversalOfId` is unique), rejects consumed or negative balances, and cannot reverse a legacy baseline or a reversal. Historical orders whose split cannot be reconstructed keep their tracking and are marked `legacyBaseline` without invented prices, actors, or times. Destination branches never create extra order-level finance holds, postings, or supplier payments; the order keeps exactly one reservation `money_movement` and one settlement pair.

Deletion exists only for nested rows: `DELETE /order/purchase-orders/:uuid/lines/:lineUuid?version=` and `DELETE /order/purchase-orders/:uuid/extra-lines/:lineUuid?version=` still run under the open-order and stored-version rules, and a line that already received stock cannot be deleted. Every route uses the `tenant: true` actor and scopes reads and writes by `organizationId`; branch origin/destination is an additional explicit `branchId` scope, and `X-Branch-Id` is validated by the branch guard when it narrows operational behavior.

## Sales

A sale is a completed restaurant preparation, not a factory order. `src/modules/sales/` keeps `controller.ts`, `service.ts`, and `model.ts`, plus optional pure formatters. `channels/` owns the organization sales-channel catalog and `batches/` owns uploaded workbook drafts, preview analysis, processing, reversal and the private source file. There are no line, allocation, output, or status submodules for a single sale.
The user-facing module, routes, and symbols are sales (`SalesService`, `SalesModel`, and `salesController`). The Prisma models `Build`, `BuildComponent`, and `BuildConsumption` and their `build`, `build_component`, and `build_consumption` tables keep those physical names. A sale always belongs to exactly one branch: `POST /sales/` requires a valid active `X-Branch-Id`, while reads and receipts accept it optionally and then return 404 for another branch's sale (`GET /sales/` filters the list). A new sale writes the required `branchId` plus the immutable `requestedRecipeUuid` (required, no foreign key) alongside the retained internal `requestedRecipeId` (the canonical selector id: company root or branch-local recipe), nullable live `recipeId` (`onDelete: SetNull`) pointing at the effective definition row, the `recipeName`, `recipeVersion`, and `ingredientCount` (the number of frozen leaf ingredient rows) snapshots, and the provenance pair `recipeDefinitionUuid` (the effective definition UUID: company root UUID when uncustomized, the customization UUID when customized, the local UUID otherwise) and `recipeSourceVersion` (the company version a customization was pinned at, null for shared templates and local recipes); each component and consumption also writes `recipeLineUuidRef`, `componentUuidRef`, and `itemUuidRef` from the actual live UUIDs inside the same transaction. Request and response fields use UUID recipe and ingredient identities. The old `itemId`, `requestedItemId`, `itemName`, `itemIpn`, `itemUnits`, `itemVersion`, `recipeChecksum`, and checked columns were removed from the current Prisma schema; `20261113000000_remove_legacy_schema` is the forward cleanup that drops their physical columns, and it was applied to the local `simayi-erp`/`public` database with physical deletions; this record covers the local environment only. New inserts never write them; the API does not publish them under old aliases. The `BO-{ref:04d}` reference pattern (`BUILDORDER_REFERENCE_PATTERN`), the `BUILD_SHORTAGE` error code, and the `item_tracking` ledger are retained. This cutover requires `20261109000000_restaurant_recipes`, `20261112000000_item_stock`, and `20261115000000_resource_uuids`, and nested ingredients additionally require `20261201000000_recipe_nested_ingredients`; the earlier stock-location/substitute removal still requires `20261107000000_recipe_stock_sales`; do not skip any of them during deployment.
`GET /sales/` lists recorded sales with bounded `limit`, `offset`, and `search`; a branch context lists only that branch while company context aggregates every branch. Each summary is `{ uuid, reference, referenceInt, recipeUuid, recipeName, recipeVersion, quantity, ingredientCount, branch: { uuid, name }, currencyCode, totalPrice, channelUuid, channelName, businessDate, batchUuid, batchReference, sourceSheet, sourceRow, sourceChannelText, sourceProductText, createdAt, createdById, createdByName }`; `currencyCode` and `totalPrice` are null on historical sales whose monetary value is unknown. `channelUuid`/`channelName`, `businessDate` and the batch/source fields are null on historical manual sales whose channel, business date or workbook origin are unknown; they are never backfilled. `businessDate` is a calendar `YYYY-MM-DD` string. `GET /sales/:uuid` returns one sale with its frozen ingredient snapshot and every same-organization item consumption. The detail adds `unitPrice`, `recipeDefinitionUuid`, `recipeSourceVersion`, `ingredients: [{ uuid, recipeLineUuid, itemUuid, itemName, itemIpn, itemUnits, quantityPerRecipe, requiredQuantity, consumedQuantity, note }]`, `consumptionCount`, and `consumptions: [{ uuid, buildComponentUuid, itemUuidRef, itemUuid, quantity, quantityBefore, quantityAfter, createdAt, createdById, createdByName }]`.
The body is `{ recipeUuid, channelUuid, quantity, requestKey }`. `channelUuid` must be an active same-organization channel; the server sets `businessDate` to the current UTC calendar day. The sold root recipe must also be marked `sellable` and active in that branch: a non-sellable root is rejected with 422 `RECIPE_NOT_SELLABLE` before any write, while nested ingredient recipes are expanded without requiring sellability, a price, or a currency of their own. The recipe must also carry a selling price in the fixed system currency at recording time: that unit price, the exact `unitPrice × quantity` total rounded to six places and the currency code are frozen into `build.unit_price`, `build.total_price` and `build.currency_code` in the same transaction. An unpriced recipe or a recipe/finance currency mismatch is rejected before any write (422; a stored finance code that differs from the fixed system currency is 409), and both manual and batch sales use this one path. Historical sales keep `NULL` there and are never repriced; a request-key replay returns the stored snapshot even after the recipe price or recipe itself changed. `POST /sales/:uuid/receipts/` records one partial or full receipt `{ amount, date, note?, requestKey }` in the finance currency; it is rejected when the sale has no recorded price, when a receipt would exceed the exact outstanding amount, or when the currency does not match, and it posts only a cash inflow (never a second income entry). Reversing a receipt frees the outstanding amount again and is allowed once. The sale detail adds `unitPrice`, `collectedAmount`, `outstandingAmount` and the `receipts` list; summaries add nullable `currencyCode` and `totalPrice`. `quantity` is a positive integer and `requestKey` is one client-generated idempotency key per user intent, unique per organization. The same key with the same branch, recipe UUID, channel UUID and quantity returns the existing sale without another deduction; the same key with a different branch, recipe, channel or quantity returns 409. Replay compares the stored branch, immutable recipe UUID, quantity and channel before any live lookup. `recipeUuid` is the effective selector UUID; a company template that is not activated in the branch, a customization-row UUID, and another branch's local recipe are rejected.
The server generates the `BO-{ref:04d}` reference and stores the staff creator, timestamp, recipe name and version, each leaf recipe line's UUID and immutable link, its item UUID, labels, IPN, and the frozen unit-code snapshot (`componentUnits`, captured from the item's assigned unit code), each leaf's effective quantity per one root recipe, and its required and consumed amounts. Before any write the reachable effective recipe graph is loaded and scoped to the organization and the sale branch, then expanded recursively: a child recipe line's quantity is units of that child per one unit of its parent, so every path multiplies down to leaf items and the snapshot has one row per distinct leaf recipe line. A unit-less or inactive item, an inactive, missing, or item-less descendant, a child recipe that is not active/activated in this branch, or a child recipe with no ingredients blocks the sale with 422 instead of inventing a unit or dropping a line. It does not store a cross-ingredient cost total because units are not comparable; the sale money total is the frozen recipe price times quantity, never a cost. No customer or end-user data is stored. The sold recipe must be active and have at least one ingredient when the sale is created, and every leaf item must be an existing, active same-organization item. There is no assembly/component distinction, template, checksum, or validation precondition. Recipe edits, child-recipe edits, and deletes never alter existing sale records: the live `recipeId` link becomes null and the frozen UUID snapshot stays.
Every leaf ingredient is mandatory and its demand is the sum of every graph path that reaches it. Optional lines, substitutes, variant substitution, inherited or template chains, setup quantity, attrition, and rounding multiples do not exist. The effective per-root quantity is the exact product of the line quantities along each path, summed over paths with 80-digit intermediate precision and never rounded; the required quantity multiplies that effective amount by the integer sale quantity. Both the effective per-root and the required amount must fit `DECIMAL(15,5)` — at most five decimal places and strictly below 10^10 — and a nested amount that would need a sixth decimal place or exceed the range rejects with a descriptive 422 before any write instead of being rounded. Each distinct leaf recipe line is snapshotted with its own UUID and note: the same leaf reached by several paths is summed into one row with the effective total, while two different leaf lines that consume the same item stay separate rows, so no shared demand is lost or overwritten. Shortage checks and stock deductions aggregate the summed demand per item before comparing it with the balance.
One transaction locks the branch lifecycle guard with `BranchesService.requireActor(db, actor, { active: true })` first, then catalog/recipe/stock (814203, 814204, 814205), re-reads the reachable effective recipe graph and that branch's exact `BranchStock` balances (`ItemStockService.balances`, a missing row is exactly zero and is never written), expands it to leaves, aggregates demand per item across every path, checks every shortage before any write, deducts each leaf's required quantity through `ItemStockService.change` with an explicit `{ organizationId, branchId, userId }` scope only after that aggregated per-item check, and inserts the sale record with its ingredient and consumption rows, so a short item leaves no partial sale. Any shortage rolls the entire scope back with 409 `BUILD_SHORTAGE` and `details.shortages` amounts (ingredient name, units, required, available from the sale branch balance, missing), never stock ids; the `componentName` and `componentUnits` keys are retained so the existing stock UI error contract does not drift, even though the sale UI labels them ingredients. Each required quantity is the effective per-root quantity multiplied by the integer sale quantity; shortage comparisons and deductions use the summed demand of the item, not one path at a time. There is no lot or location selection: the selected branch's balance is the only availability source, and stock from another branch or organization is never read or written. Advisory locks run through `$executeRaw` because `pg_advisory_xact_lock` returns `void`, which the Prisma PostgreSQL adapter cannot deserialize as a `$queryRaw` result column; the lock keys, ordering, transactions, and isolation levels are unchanged.
Consumption rows record the immutable UUID `itemUuidRef` (the internal `itemRef` integer snapshot stays for joins), the live same-organization `itemId` link (`SetNull` when the item is deleted), the consumed quantity, and the aggregate `quantityBefore`/`quantityAfter` captured in the same transaction, where `before - after` equals the consumed quantity. Each leaf snapshot has one balance write in the single sale transaction, after the summed per-item shortage check, so a sale cannot partially debit or overdraw an item. No stock-item id, lot, serial, batch, expiry, or supplier snapshot is stored, and no balance record is deleted when stock reaches zero. Tracking type `12` is written in the same `item_tracking` ledger with UUID identity strings in `deltas` (`buildUuid`, `itemUuid`); the retired access trigger is dropped by `20261110000000_retire_custom_access`, so no access context is written or retained. No finished-goods balance is created and no quantity is reserved for another sale.
Consumption detail is scoped by organization and, when a branch header is present, by that branch's sale. Every same-organization consumption row of the loaded sale is returned, including rows whose live item link was detached or deleted; old owner or access flags never filter a row. The full record includes `consumptionCount`, and `consumptions` contains all same-organization rows. Recipe ingredients and the sale summary are readable by every organization member.

## Sales channels and workbook batches

Channels are organization-scoped, reusable, and never deleted while referenced; SalesChannel definitions and reusable channel mappings stay company-wide, while batches, their product mappings and their sales are branch-scoped. An explicit draft channel mapping is also stored as a reusable organization-level source-value mapping; later batches resolve only exact previously mapped source values, never by fuzzy name matching or auto-creating a channel: `GET /sales/channels/` (paged), `POST /sales/channels/` `{ name }`, and `PATCH /sales/channels/:uuid` `{ name?, active? }`. Inactive channels cannot be used by a new sale or batch.

Workbook batches accept only original `.xlsx` files up to 10 MB; each worksheet is limited to 5000 rows and 64 columns and a larger workbook is rejected explicitly instead of being truncated. `POST /sales/batches/` requires a valid active `X-Branch-Id` and permanently fixes the batch to that branch; it takes multipart `file` as its only required input, validates the ZIP/OOXML signature, parses the workbook with `read-excel-file` (all parsing and limits stay in `batches/workbook.ts`), and stores the bytes through central media under the `sales-batch-workbook` purpose with original name, size, content type, uploader, organization and expiry. The draft row and the file binding are then created in one transaction: the batch is inserted, the media row is claimed with reference `sales-batch:<batchUuid>`, and a failed create marks the upload for deferred cleanup instead of unlinking inside the transaction. `sourceFile` is internal metadata. No content, date or channel uniqueness exists: the same file uploaded twice produces independent batches with distinct references. A worksheet that matches the printed Modpos Ürün Raporu signature — the `Ürün Raporu` title above one header row that carries `Kodu`, `Ürün Tipi` and `Adedi` on the same physical row — is preselected at upload: the draft stores that worksheet, its real header row and the derived product-code, product and quantity columns, skips every row whose product-code cell is blank (Genel Toplam footers included) before any other cell is read, and uses the printed `Tarih` stamp as the business date when it names one valid calendar day. The file name is never used for detection. Every other workbook stays unconfigured with today's business date. A recognized report whose printed date is unreadable or spans more than one day keeps its derived columns, leaves the business date at today and adds a non-blocking note, so a multi-day range is never collapsed into an invented day.

`GET /sales/batches/?limit=&offset=&search=` filters the list by the request branch when one is present and aggregates every branch in company context; `GET /sales/batches/:uuid`, `/:uuid/preview` and `/:uuid/file` return 404 when a branch context names a different branch, so a batch is never read across branches. `GET /sales/batches/:uuid/preview` reads the stored workbook through central media by its batch binding and returns the raw grid, branch summary, mapped rows, per-row blocking issues, channel/product summaries and aggregate material requirements; an optional `?sheet=` explores another worksheet without changing the draft. The preview also returns the verified `modpos` header (`sheetName`, `headerRow`, the derived columns and the printed date bounds) plus non-blocking notes that quantities stay the reported `Adedi` values, `Fixler`/`İkram Adet`/`Biletler` are not applied, the `Tutar`/`B. Tutar`/`Maliyet`/`Kar`/`Kar Oranı` columns are never imported, and non-sale rows with a product code still need explicit exclusion. Preview availability is the batch branch's exact balance, the same source processing uses for its shortage check, and the persisted batch branch — not the current header — resolves the effective recipes. Preview prices always use the fixed system currency: a stored finance code in another currency, or a stored system code the catalog no longer accepts, becomes a blocking per-row issue so preview and processing agree, and the preview never creates a finance row. `PATCH /sales/batches/:uuid` requires an active branch that matches the batch branch and saves the calendar business date, worksheet name, header row, channel/product/quantity column letters, optional product-code column, explicit excluded rows, per-batch channel mappings, reusable company channel mappings, and branch product text mappings (`UNIQUE(organization_id, branch_id, product_key)`, `text:` identity only, never fuzzy name linking). The channel column may be `null` only while the saved worksheet, header row and columns are exactly the verified Modpos header; such a report then uses one fixed `Modpos` source value that must be mapped to an active channel through the same explicit mapping, so a report column can never turn into a channel by accident. A product mapping target must be an active effective recipe of that branch, the stored canonical recipe identity (company root or that branch's local recipe) is what follows later activation/customization/reset, and clearing a mapping never touches another branch. A row whose workbook product-code cell is nonempty resolves only by the exact, case-sensitive effective `Recipe.code` of the batch branch: leading zeros stay significant, a different product name never changes the match, and a saved manual `code:` mapping can neither override the match nor stand in when no code matches. A company root and its branch customization are one canonical candidate; an override that changed the code does not match the obsolete root code. Candidates keep their effective activation, so an exact identity is not lost merely because the recipe is inactive: active exact-code candidates are preferred, an inactive duplicate never hides an active match, and only when no candidate is active does a unique inactive one resolve. No candidate adds blocking `PRODUCT_CODE_UNMATCHED` (`No recipe matches this product code in this branch`); more than one active candidate, or no active candidate with more than one inactive candidate, adds blocking `PRODUCT_CODE_AMBIGUOUS` (`More than one active recipe matches this product code in this branch` / `More than one inactive recipe matches this product code in this branch`). A code that resolves to an inactive recipe adds blocking `RECIPE_INACTIVE` (`This recipe is not active for the selected branch and cannot be sold`) while keeping its UUID and name resolved, and a resolved recipe not marked `sellable` adds blocking `RECIPE_NOT_SELLABLE` (`This recipe is not marked as sellable`) instead of looking unmatched; the same issue blocks a code-less row whose exact `text:` mapping resolves to a non-sellable recipe. Activation and sellability are independent gates, so one resolved row can carry both `RECIPE_INACTIVE` and `RECIPE_NOT_SELLABLE`. The missing-price/currency checks and the previewed amount apply only to sellable recipes, so a non-sellable definition is never required to carry a price even when it is also inactive; its exact code/name stays resolved and its stock requirements are not planned. The aggregate shortage against the batch branch balance is attributed to every otherwise-valid included row that contributes one of the short items, using the same single balance read as the requirement summary, as blocking `STOCK_SHORTAGE` (`This row requires ingredients with insufficient branch stock`); no per-row query or separate per-row shortage check is added, and the blocking issue count includes those rows. A new non-null manual mapping for a `code:` key is rejected with `Coded products are matched by recipe code and cannot be mapped manually`; clearing a legacy code mapping stays possible, exact `text:` mappings apply only while no product-code column is configured, and with a configured product-code column a blank-code row is never parsed. Candidate codes are fetched with two organization/branch-scoped queries and resolved through the same single effective graph the analysis already loads, never with one query per row, and preview and processing share that resolver. `POST /sales/batches/:uuid/process` requires the same active matching branch, takes the branch lifecycle guard then catalog, recipe and stock locks, reloads the draft, rejects any blocking row issue or aggregate shortage against the batch branch balance, writes every included row through the shared `SalesService.plan`/`create` path in one transaction, and marks the batch processed; every generated sale carries the batch branch and the frozen effective definition/price provenance. Preview and processing load the reachable recipe graph once per analysis and expand every mapped root to leaf items, so preview requirements, aggregate shortage checks and the written snapshots all use the same summed per-item demand; an invalid nested graph is a per-row `RECIPE_INVALID` blocking issue instead of aborting the whole preview. Its deterministic per-row `requestKey` and conditional draft-to-processed update prevent double processing.

`DELETE /sales/batches/:uuid` requires an active branch that matches the batch branch and removes a draft with no stock effect. A processed batch whose sales have any receipt history cannot be deleted at all, even when every receipt was reversed, because reversal rows stay as immutable financial history and the `money_movement.build_id` foreign key is `RESTRICT`; delete takes the finance advisory lock after the stock lock so a concurrent receipt cannot interleave. A batch with any linked bank POS Z report is also refused before any stock reversal, with 409 `SALES_BATCH_Z_REPORTS` and `details.reportCount`, so the reports can be detached deliberately first; the report's composite `ON DELETE RESTRICT` foreign key is the authoritative guard against a concurrent attach. Otherwise it appends exact recorded consumption quantities back into each sale's original branch through `ItemStockService.change('add')` with `sale-batch-reversal` deltas (the build branch is frozen and the database trigger keeps it equal to the batch branch), fails atomically when an original item no longer exists, and deletes consumption, component and build rows explicitly in that order before the channels and batch because `build_consumption.build_component_id` is `ON DELETE NO ACTION`. Deleting a batch releases its workbook binding in the same database transaction, only after the batch row itself is deleted; the bytes are never unlinked inside the transaction and are removed later by `media:cleanup`. `GET /sales/batches/:uuid/file` streams the original workbook for the same organization with `Content-Disposition: attachment` and is not reachable through the global logo media endpoint.

The additive `20261122000000_sales_batches` migration creates `sales_channel`, `sales_channel_mapping`, `sales_batch`, `sales_batch_channel` and `sales_product_mapping` and adds nullable batch/channel/business-date/source columns to `build`. Existing rows stay null. The later `20261202000000_company_branches` migration makes `sales_batch.branch_id` and `sales_product_mapping.branch_id` required (backfilled with the organization's initial branch), replaces the mapping uniqueness with `(organization_id, branch_id, product_key)`, makes `build.branch_id` required, and adds a trigger keeping a sale's branch equal to its batch branch; existing batches, mappings and sales are assigned to the initial branch and no reference, quantity or snapshot is rewritten.

## Finance

`src/modules/finance/` keeps `controller.ts`, `service.ts`, `model.ts`, a pure `formatter.ts`, and the `suppliers/` submodule with its own controller/service/model; `app.ts` still mounts only the root `financeController`, which composes the supplier-ledger subcontroller. Every route uses the `tenant: true` actor and scopes reads and writes by the explicit `organizationId`; there is no permission scope, dynamic role or record-owner check. Finance is deliberately company-wide: cash, debt and currency are never split or filtered per branch, so `/finance/` and `/finance/movements/` ignore `X-Branch-Id` for scoping.

| Endpoint | Authority / purpose |
| --- | --- |
| `GET /finance/` | Active organization finance summary: `{ configured, currencyCode, balance, onHold, availableBalance, movementCount, pendingPricingCount }`. Never creates the finance row; `currencyCode` stays `null` until the first financial write. `balance` is the exact sum of posted rows, `onHold` the positive amount still reserved by open purchase orders, `availableBalance` is `balance − onHold`, `movementCount` counts posted rows, and `pendingPricingCount` counts on-hold orders whose hold is incomplete. Every value is an exact decimal string and `"0"` for an empty or unconfigured organization. |
| `GET /finance/movements/?limit=&offset=&search=` | Paginated movements in the finance currency, newest first, including on-hold and cancelled purchase reservations. `search` matches note, supplier name, purchase order reference and sale reference. |
| `GET /finance/movements/:uuid` | One movement with its `status` (`on_hold`, `posted` or `cancelled`), its purchase order link and pending-pricing fields, its single reversal link and whether it `reversible`. |
| `POST /finance/income/`, `POST /finance/expense/` | General income or expense `{ amount, date, note?, requestKey }`; income posts a positive amount and expense the same exact negative amount. Neither is a sale receipt or a supplier payment. |
| `POST /finance/movements/:uuid/reverse` | Posts one linked reversal, at most once, for a posted entry only. A supplier payment reversal also reverses its ledger entry in the same transaction. A posted purchase restores its cash and reverses its auto-posted settlement credit while the purchase debit and the order's recorded prices stay untouched; an on-hold or cancelled reservation and a zero-value purchase row cannot be reversed. |
| `GET /supplier/:uuid/ledger/?limit=&offset=` | Paginated supplier ledger in the finance currency with `configured`, `currencyCode`, `outstanding` and the entry list. The outstanding balance is always an exact decimal string, `"0"` for a supplier with no posted entries or an unconfigured organization, and may be negative (a supplier credit/advance). |
| `POST /supplier/:uuid/payments/` | Supplier payment `{ amount, date, note?, requestKey }`. One transaction posts the exact cash outflow and the same debt reduction; paying above the debt leaves a supplier credit and is not capped at zero. |

Every movement response also carries the provenance of the linked document as flat `branchUuid: string | null` and `branchName: string | null`: a sale receipt (and its reversal) reports the original sale branch, a purchase reports the order origin branch, and manual income/expense or a supplier payment without an order is null. This is never inferred from the current request context. When a sale receipt is requested with a branch context, the loaded sale must belong to that branch or the receipt fails closed with 404; without a branch header the receipt stays an explicit company finance action. Reversals copy `buildId`/`purchaseOrderId`, so their provenance is the original document's branch and a correction never reclassifies money. Supplier ledger entries expose the same two fields from the linked purchase-order origin.

`OrganizationFinance` (`organization_finance`) is one row per organization: internal integer `id`, public `uuid`, unique `organizationId`, `currencyCode` and `createdAt`. Every explicit financial write (income, expense, supplier payment, sale recording, sale receipt, purchase order creation and completion) uses the fixed system currency through `SystemPreferencesService.requireCurrency`; the first write creates the `organization_finance` row with that code, and a read never creates it. A stored finance code that differs from the fixed system currency is a legacy conflict: new writes fail with 409 instead of mixing currencies, and recorded history is never relabelled. Mixed-currency sums are impossible because every financial write also requires the line, recipe or sale snapshot it touches to use the same code.

`MoneyMovement` (`money_movement`) stores one cash entry in the finance currency. Positive amounts are cash inflow and negative amounts cash outflow; the balance is the exact sum of posted rows, never an editable field. `entryKind` is `20` income, `30` expense, `40` supplier payment, `50` sale receipt, `60` purchase or `90` reversal. Only kind `60` carries the reservation lifecycle in `status` (`10` on hold, `20` posted, `30` cancelled): one row per order, negative or zero, created with the order and refreshed by its priced writes, and every other kind stays `20` and is posted on creation. `pricingIncomplete` and `pricingIssueCount` mark a hold whose known amount is incomplete because a line has no price, no recorded currency or another currency. `SupplierLedgerEntry` (`supplier_ledger_entry`) stores the payable side in the same currency: positive increases what we owe, negative reduces it, with kinds `20` purchase, `30` payment and `90` reversal. Both tables are append-only for every financial fact; the single mutable row is the on-hold purchase row, whose amount, supplier link and pricing flags the order's writes refresh, and which then becomes posted (exactly once) or cancelled. A posted or cancelled row is never rewritten. A reversal row carries the negated amount, the same supplier/sale/purchase links and a unique `reversal_of_id`, so an original row is reversed at most once and every total stays exact. Database constraints also enforce `amount <> 0` except for a purchase row, the kind allowlist, the currency shape, reversal consistency, one purchase row and one auto settlement payment per order, and unique `(organization_id, request_key)`; a replayed request key returns the original entry and a different kind or source with the same key returns 409.

Mutations take the finance advisory lock `814207` through `$executeRaw` (the same void-result reason as the other locks) and run at `READ COMMITTED`. The documented global order is branch lifecycle (`814209` + branch id; only branch writes) → order `814206` → category `814202` → item `814203` → recipe `814204` → stock `814205` → finance `814207`; no transaction acquires an earlier lock after a later one. Manual sale and batch sale paths capture the price after the stock lock, purchase creation, line/extra/header writes and purchase completion take the finance lock after the order and stock locks, and receipt/payment/reversal transactions take only the finance lock. The additive `20261123000000_finance_ledger` migration creates these three tables, adds nullable `recipe.selling_price`/`recipe.price_currency_code` and nullable `build.unit_price`/`build.total_price`/`build.currency_code` with shape/range checks, and backfills nothing; this document does not record it as applied to any database. The forward `20261124000000_remove_opening_balances` migration deletes only legacy opening rows (`entry_kind = 10`) and their own linked reversals, drops the opening-only unique indexes, recreates both entry-kind CHECK constraints without kind `10`, and leaves every other financial row untouched. The forward `20261129000000_purchase_finance_holds` migration adds `money_movement.status`, `purchase_order_id`, `pricing_incomplete` and `pricing_issue_count`, defaults every existing movement to posted (`20`), allows only a purchase row to leave that status, to carry a zero amount and to be negative-or-zero, adds the status/sign/source/pricing CHECKs, the purchase-order foreign key and the one-row-per-order and one-settlement-per-order unique indexes, then reserves each still-active order (`10`/`20`/`25`) whose organization finance code equals the configured system currency with the sum of its priced lines in that one code; lines with no price, no currency or another currency are counted as pricing issues, and organizations without a matching finance row, completed orders, cancelled orders and historical rows receive nothing. The local development database (`localhost:5432`, database `simayi-erp`, schema `public`) already has this migration applied through `bun run db:deploy`; any other environment must still run that step.

## POS devices and Z reports

`src/modules/pos-devices/` keeps `controller.ts`, `service.ts`, `model.ts`, and a pure `formatter.ts`, with the nested `z-reports/` submodule owning the report controller/service/model/formatter. `app.ts` mounts only `posDevicesController`; it composes `posDeviceZReportsController` with `.use(...)`. Both controllers use the `tenant: true` actor; reads are scoped by `organizationId` and an optional `X-Branch-Id` narrows them to one same-company branch, while every write still requires a resolved active branch, scopes by `organizationId + branchId`, and takes the branch lifecycle guard first inside each write transaction. Reads resolve inactive branches, writes require an active one. There is no permission scope, dynamic role, or record-owner check.

A bank POS device (`pos_device`) is one card terminal: internal integer `id`, public `uuid`, `organizationId`, required immutable `branchId` (reported as `branch: { uuid, name, active }`), `name` (at most 100, nonblank), `bankName` (at most 100, nonblank), `terminalId` (at most 100, nonblank), `active` (default true), `version` (default 0), and timestamptz `createdAt`/`updatedAt`. It is a bank terminal record, not a fiscal receipt printer: no hardware protocol, certificate, payment or settlement integration exists. There is no device delete route; deactivating keeps every historical report readable.

A Z report (`pos_device_z_report`) is bank end-of-day reconciliation evidence: internal integer `id`, public `uuid`, `organizationId`, `posDeviceId`, nullable `salesBatchId`, `reportNumber` (`VARCHAR(100)`), `businessDate` (`DATE`), `closedAt` (`TIMESTAMPTZ(6)`), `totalAmount` (`DECIMAL(19,6)`), `currencyCode` (`VARCHAR(3)`, creation-time snapshot), `note` (`VARCHAR(500)`), `version`, and timestamps. `UNIQUE(organization_id, pos_device_id, report_number)` rejects the same report number twice for one device, including concurrent writes (translated to 409). Both tenant links are composite foreign keys: `(organization_id, pos_device_id)` → `pos_device` and `(organization_id, sales_batch_id)` → `sales_batch`, both `ON DELETE RESTRICT`, so a report can never reference another organization's device or batch. The report stores no `branchId`: its branch is derived from the immutable device link (reported as `branch: { uuid, name, active }`), and a database trigger requires a linked batch to belong to the same branch as the device, so a cross-branch attachment is impossible even outside the service.

| --- | --- |

Response `{ items, total, limit, offset }` with each item `{ uuid, name, bankName, terminalId, active, version, branch: { uuid, name, active }, createdAt, updatedAt }`. |
| `GET /pos-devices/:deviceUuid` | Company context resolves any same-organization device; with `X-Branch-Id` another branch's device is 404. |

| `PATCH /pos-devices/:deviceUuid` | Full body `{ name, bankName, terminalId, active, version }`. The stored `version` must match or the request returns 409; one successful write increments it once. Missing `version` fails schema validation (422). The branch is immutable and never accepted. |

Validation is exact: `reportNumber` is trimmed to 1–100 characters; `businessDate` is a real `YYYY-MM-DD` calendar date; `closedAt` is an RFC 3339 date-time with an explicit timezone; `totalAmount` is a nonnegative plain decimal string with at most 13 integer and 6 fraction digits (the `DECIMAL(19,6)` bound, never a JavaScript number); `note` is trimmed to at most 500 characters; `salesBatchUuid` is a UUID or `null`. Responses return `businessDate` as a day string, `closedAt`/`createdAt`/`updatedAt` as ISO date-times, `totalAmount` as an exact string, `posDevice: { uuid, name }`, derived `branch: { uuid, name, active }`, and `salesBatch: { uuid, reference, businessDate, status } | null`.

A report belongs to exactly one device and at most one sales batch, while one batch may have many reports and partial coverage is expected. Creating a report reads the fixed system currency through `SystemPreferencesService.requireCurrency` and snapshots it as `currencyCode`; it creates no `organization_finance` row and posts no money movement. Editing a report does not read the currency at all and keeps the stored snapshot unchanged. There is no sale-level link, allocation, split, automatic matching, balance/matched/completed claim, or money movement: reports are reconciliation evidence only. There is no report or device delete route.

This document does not record either migration as applied to any database.

## Dashboard

`src/modules/dashboard/` keeps `controller.ts`, `service.ts`, and `model.ts` for the platform and membership summaries, plus nested `layout/` and `analytics/` submodules for the personal dashboard builder. Each submodule has its own controller/service/model; `app.ts` still mounts only the root `dashboardController`, which composes the subcontrollers with `.use(...)`. No formatter is required: every response is a computed aggregate or a validated JSON layout rather than a persisted-row projection.

`GET /dashboard/system` and `GET /dashboard/personal` are the explicit, narrow aggregate exception to the rule that business data is organization-scoped. They expose only the totals and alert fields below, never raw business rows, personal metadata, or general cross-organization access, and they add no business authorization layer. The personal dashboard layout/catalog/data endpoints store an owner-private layout preference and execute curated aggregates; global variants use `auth: true` without a tenant header, and organization variants use `tenant: true` with the resolved `TenantActor`. None of these endpoints exposes raw business rows, and every other business route keeps `tenant: true` and the same-organization `organizationId` boundary.

| Endpoint                | Authority / purpose                                                                                                                                  |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /dashboard/system` | Platform administrator only (`UsersService.requireAdministrator(user.role)` runs before any query). All-time counts for users, organizations, sales, and purchases, plus six monthly new-record counts. |
| `GET /dashboard/personal` | Any active account. All-time sales and purchase counts plus low-stock alerts for the organizations where that user currently has a native `member` row. |
| `GET /dashboard/layout`, `PUT /dashboard/layout` | `auth: true`. Read or save the session user's global dashboard layout. PUT accepts `{ expectedRevision, definition }` and reports stale or simultaneous saves as 409. |
| `GET /dashboard/catalog`, `POST /dashboard/data` | `auth: true`. Server-owned global widget capabilities and one bounded batch of at most 24 widget aggregates. |
| `GET /dashboard/organization/layout`, `PUT /dashboard/organization/layout` | `tenant: true`. Read or save the session user's personal layout inside the active organization; the tenant comes from `TenantActor`, never the request body. |
| `GET /dashboard/organization/catalog`, `POST /dashboard/organization/data` | `tenant: true`. Organization-scoped catalog and bounded widget aggregates. The data endpoint applies an optional verified `X-Branch-Id` (branch stock positions, sales of that branch, purchase orders whose origin is that branch); without it the aggregate is the explicit company roll-up. Catalog and layout ignore the branch header. |

`GET /dashboard/system` returns `{ totals: { users, organizations, sales, purchases }, months: [{ month, users, organizations, sales, purchases }] }`. `totals` are all-time `COUNT(*)` values. `months` always has exactly six entries for the current UTC month and the five prior months, ordered oldest first, and every month is zero-filled from the actual grouped counts. `month` is the `YYYY-MM` UTC key. Monthly `users` and `organizations` count new `User.createdAt` and `Organization.createdAt` rows, `sales` counts `Build.createdAt`, and `purchases` counts `PurchaseOrder.creationDate`; a null purchase creation date stays in the all-time total but is excluded from the monthly series. Aggregation runs in PostgreSQL with bounded grouped results; the API never loads all rows to count them in memory.

`GET /dashboard/personal` returns `{ totals: { sales, purchases }, alerts: { total, items } }`. Every business query evaluates current membership in its own database statement: the two Prisma counts use the native relation filter `organization.members.some.userId`, and both alert queries use `EXISTS (SELECT 1 FROM member ...)` for the same `userId`. No membership ids are preloaded or reused, a removed membership cannot expose the previous organization on a later read, and a user with no membership naturally gets `{ totals: { sales: 0, purchases: 0 }, alerts: { total: 0, items: [] } }`. There is no owner, creator, or status filter, so all members of an organization see the same scoped summary. `totals.purchases` includes every purchase-order status; `totals.sales` counts all `Build` rows in organizations where the user currently has a native `member` row.

`alerts` covers active catalog items in each active branch of a company the user currently belongs to, using the branch balance (`branch_stock`) where a missing row reads zero stock and zero minimum. The comparison is a real `COALESCE(stock,0) <= COALESCE(minimum_stock,0)` predicate in PostgreSQL, matching the stock screen's `low` filter, so zero-row positions are reported rather than dropped. `total` is the full matching count and `items` is a deterministic bounded list of at most eight rows ordered by largest shortfall (`minimumStock - stock`) descending, then name, then branch name, then UUID. Each item is `{ uuid, name, ipn, stock, minimumStock, units, organizationName, organizationSlug, branchUuid, branchName }`; `ipn` keeps its database nullability, `units` is the assigned global unit code read through `LEFT JOIN "unit" ON "unit".id = "part".unit_id` and stays null when the item is unresolved, `stock` and `minimumStock` are exact decimal strings, and `uuid` plus `organizationSlug`/`branchUuid` are the identifiers the frontend needs to open the stock page in the correct branch. No internal business integer id or cross-organization row is returned. Database and query errors propagate; a failed query never becomes a zero-filled success.

### Personal dashboard builder

One saved dashboard per account and context is stored in the `Dashboard` Prisma model and the additive `20261116000000_personal_dashboards` migration: internal integer `id`, database-generated public `uuid`, native `user_id` foreign key, nullable native `organization_id` (null is the global dashboard), `schema_version`, `revision`, JSONB `definition`, and timestamptz `created_at`/`updated_at`. The compound unique index `(user_id, organization_id)` covers organization-scoped rows, and the partial unique index on `user_id` where `organization_id IS NULL` enforces exactly one global row despite PostgreSQL's distinct-NULL semantics. Check constraints require `schema_version = 3`, `revision >= 1`, a JSON object definition, and `definition ->> 'version' = '3'`. The follow-up `20261117000000_dashboard_grid_positions` migration rewrote existing definitions to version 2 and set the column default to 2; it creates no table or column. The final `20261118000000_dashboard_native_dimensions` migration rewrote every stored widget's `width`/`height` enums into the equivalent native `w`/`h` integers, bumped each row's `revision`, and moved the column default and both checks to 3; it also creates no table, column, or index. Deleting the native user or organization cascades to these personal preference rows. No integer identifier crosses the HTTP boundary; widget ids are client-generated UUIDs inside the JSON definition, not database rows.

The layout owner is always the verified session user; no request body accepts a user or organization owner selector. A global route stores `organizationId = null`; an organization route takes the organization only from `TenantActor`. A preference row is visible only to its owner and never grants, filters, or restricts business-record access. Shared, team, and multiple layouts are not implemented by design.

`GET /dashboard/layout` and `GET /dashboard/organization/layout` return `{ dashboard: { uuid, schemaVersion, revision, definition, savedAt, updatedAt } }`. When no row exists they return the explicit unsaved default `{ uuid: null, schemaVersion: 3, revision: 0, definition: <real-data default>, savedAt: null, updatedAt: null }` and do not write. The default contains real catalog-valid cards for the context. `PUT` accepts only `{ expectedRevision, definition }`; `expectedRevision: 0` creates atomically and a simultaneous create returns 409, while an update uses `WHERE revision = expectedRevision` and a stale value returns 409 with no overwrite. The successful response is the newly saved revision. Failed or conflicting saves leave the client draft intact.

A definition is `{ version: 3, widgets: [...] }` with at most 24 widgets, unique widget UUIDs, titles of 1–80 characters, and explicit native grid geometry: `x` (0–3 starting column), `y` (starting row), `w` (1–4 columns) and `h` (any positive whole number of rows). Every visual type may use every width and height. `x + w <= 4` is the only column rule, and `y`/`h` only have to be safe integers: there is no row cap, per-type limit, or presentation preset. Each widget also carries `type` (`kpi|column|bar|line|donut`), `source` (`sales|purchases|stock`), a source-specific `measure`, optional `groupBy`, optional `seriesBy` (`status`), optional `dateRange`, and a status filter list. Coordinates that leave the four columns or any overlapping pair of cards are rejected with rectangle-pair checks, as are unsupported source/measure/type/grouping/range combinations, non-temporal line charts, temporal donut charts, status series on non-temporal charts, unknown or duplicate purchase statuses, and stock date filters. Persisted JSON that no longer validates is reported as a server error and is never silently replaced with defaults. An empty widget list is a valid saved dashboard.

The backend-owned catalog exposes the only available capabilities for a context. Initial sources: sales count and, in organization scope, sold recipe-quantity sum (`Build.quantity`); purchase-order count; current active critical-position count in both scopes and active item count in organization scope. A critical position is one branch/item balance, or one item per active branch when no row exists, where `COALESCE(stock,0) <= COALESCE(minimum_stock,0)`; `active_item_count` is the shared catalog size and is never multiplied by branches. In branch context sales are filtered by sale branch and purchases by order origin branch; company context aggregates every branch once. Temporal groupings are UTC day, week, and month for sales and purchases; organization scope also groups sales by the immutable `requestedRecipeUuid` snapshot (latest frozen `recipeName` label, never merged by name) and purchases by native status or supplier (explicit no-supplier bucket). Global stock groups critical counts by current member organization; organization stock groups item counts by category UUID with an explicit uncategorized bucket. Date presets use half-open UTC intervals: `last_30_days`, `last_90_days`, `last_6_months`, `last_12_months`, plus `all_time` for KPI and categorical grouping. Temporal charts accept only ranges allowed by their granularity (daily long ranges are rejected); all-time temporal charts are not offered. Missing temporal buckets are zero-filled in the service. Purchase `creation_date` is a nullable SQL `DATE`: null dates are excluded from dated charts and ranged counts but included in all-time counts.

Categorical grouping is bounded in PostgreSQL to the top ten values plus one exact `Other` bucket using UUIDs or semantic native values, never internal integer ids. The head buckets keep their deterministic rank order and `Other` is last; ties break on label and key. Sales recipe grouping applies the selected measure (sale count or summed `Build.quantity`) while retaining immutable recipe UUID identity, and its latest snapshot label is selected with a bounded per-group `ORDER BY ... LIMIT 1`. Every aggregate query adds the tenant predicate or, in global scope, a live `EXISTS` membership predicate to each business read; no client membership list is trusted. Sale, purchase, and stock reads group over their own root rows, so line items cannot inflate counts. Measures are nonnegative integers returned as numbers; no prices, currency, stock-balance sums across units, arbitrary SQL, formulas, telemetry, or caching layer is added.

`POST /dashboard/data` and `POST /dashboard/organization/data` accept at most 24 widget configurations and return `{ asOf, results }`. Each result is keyed by widget UUID and includes the visual type, measure label, unit label, total, temporal flag/granularity, range label, date basis, category labels, aligned series values, and the same `asOf` timestamp. Identical aggregate configurations inside a batch reuse one query. The endpoint never returns raw business rows. A failed query propagates as an error instead of becoming zero-filled data; an aggregate that genuinely has no matching rows still returns bounded zero buckets where the widget is temporal.

All three dashboard migrations were applied once to the local `simayi-erp`/`public` PostgreSQL database only after confirming each was the sole pending migration (`bun run db:deploy`). `20261116000000_personal_dashboards` created only the new table. `20261117000000_dashboard_grid_positions` created no table or column: it rewrote existing v1 definitions to v2 grid coordinates, bumped each row's `revision`, moved the column default and check to 2, and added a check that the JSON version agrees with `schema_version`. `20261118000000_dashboard_native_dimensions` also created no table, column, or index: it replaced each stored widget's `width`/`height` enums with the equivalent native `w`/`h` integers, bumped each row's `revision` once, and moved the column default and both checks to 3. The local database already held saved layout rows for an organization and for the global scope; every widget UUID, title, type, option, `x`/`y` value and array position in them was preserved, the converted sizes match the old enum spans exactly, no `width`/`height` key remains, and both rows now validate as version 3 with non-overlapping geometry. No other environment is claimed. Prisma Client and Prismabox generation were rerun after the schema change.



## Security and service checks

- The custom `plugins/security.ts` origin/header hook is removed. Better Auth's `trustedOrigins` and built-in CSRF checks protect `/auth/*`; unsafe requests there reject untrusted origins and unsafe cookie requests require a trusted origin.
- CORS uses `trustedOrigins`, credentials, and the documented request headers; it is unrelated to the removed custom permission layer.
- The OpenAPI document keeps its `cookieAuth` security scheme.
- `/health` reports process liveness. `/ready` checks PostgreSQL and Redis within 3 seconds.
- Bun limits request bodies to 1 MiB and idle connections to 30 seconds.
- SIGINT and SIGTERM stop the server and close resources within a 10-second deadline.
- JSON logs record status codes and safe error frames, plus the fixed Prisma request code (for example `P2010`) for `PrismaClientKnownRequestError`; messages, metadata, SQL, headers, and bodies are never logged.

Do not expose dependency ports to the public network.

## Production deployment

Use one API instance behind a TLS reverse proxy. Use managed or private PostgreSQL and Redis services.
The Compose file is for development only. Its credentials are not production credentials.

1. Supply production environment variables through the deployment secret store.
2. Install dependencies with `bun install --frozen-lockfile`.
3. Run `bun run db:generate` from `apps/api`.
4. Run `bun run build` and `bun run lint`.
5. Run `bun run db:deploy` once before the new instance starts.
The local `localhost:5432` database `simayi-erp` / `public` has `20261201000000_recipe_nested_ingredients` and `20261202000000_company_branches` applied; the backup and deployment record is in `../../docs/company-branch-cutover.md`. This does not establish the state of any other environment. Deploy it in a maintenance window with every API writer stopped and a verified database (and `MEDIA_ROOT`) backup: `bun run db:deploy`, then start the new API/web build. Do not start the old build after the migration: it still reads `part.stock`/`part.minimum_stock`, which the migration removes after moving the exact balances into the deterministic initial branch of each organization. The migration preserves organization/member/team identity, row ids, UUID snapshots, currencies and historical quantities; it never merges companies/items/recipes, invents receipt prices/actors/times, or copies one old balance into several branches.
6. Run `bun run start` under the process supervisor.
7. Use `/health` for liveness and `/ready` for readiness.

`build` checks types. Bun runs TypeScript directly, so no compiled artifact is required.
Production disables OpenAPI endpoints and enables secure cookies and HSTS.
Configure proxy body limits, request timeouts, log collection, dependency backups, and alerts in the deployment platform.
